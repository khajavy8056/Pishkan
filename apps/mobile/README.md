# اپ اندروید مشتریان پیشخوان (نیتیو Flutter)

اپ **کاملاً نیتیو** اندروید برای **مشتریان** — بدون WebView. به همان بک‌اند، همان دیتابیس و همان
کاربران نسخهٔ وب وصل می‌شود: با همان شماره موبایل و رمزی که در سایت دارید وارد می‌شوید و
درخواست‌ها/پرداخت‌ها/مدارک در هر دو طرف دقیقاً یکی است. همکاران و مدیران روی پنل وب می‌مانند
(اپ حساب کارمندی را قبول نمی‌کند).

مدیریت اپ (استوری‌ها و اطلاعیه، آمار استفاده، نسخهٔ اجباری، متن خوش‌آمد) از پنل مدیر کل:
**«اپ اندروید مشتریان»** (`/admin/android-app`). وبلاگ عمداً در اپ نیست.

## یک‌بار: فعال‌سازی بیلد خودکار (GitHub Actions)

فایل ورک‌فلو به دلیل محدودیت دسترسی توکن محیط توسعه داخل `ci/` نگه داشته شده است. یک‌بار:

1. در GitHub ریپو: **Add file → Create new file**
2. مسیر را بنویسید: `.github/workflows/android.yml`
3. محتوای `apps/mobile/ci/android.workflow.yml` را کامل کپی و Paste کنید → Commit.

همین! از این به بعد هر تغییری در `apps/mobile` یک بیلد کامل (analyze + تست + APK/AAB)
در تب **Actions** می‌سازد و خروجی‌ها از بخش **Artifacts** همان اجرا قابل دانلودند.

### امضای رسمی (قبل از انتشار عمومی، حتماً)

در **Settings → Secrets and variables → Actions** این چهار سکرت را بسازید
(کلید آماده با راهنما در پوشهٔ `pishkan-signing-backup` بیرون ریپو تحویل داده شده است):

| سکرت | مقدار |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | محتوای base64 فایل کلید `.p12` |
| `ANDROID_KEYSTORE_PASSWORD` | رمز فایل کلید |
| `ANDROID_KEY_PASSWORD` | رمز کلید (همان) |
| `ANDROID_KEY_ALIAS` | `pishkan` |

بدون این سکرت‌ها بیلد با کلید دیباگ امضا می‌شود: برای تست کافی است، اما برای انتشار
عمومی/فروشگاه و برای اینکه آپدیت‌های بعدی روی نصب قبلی بنشینند، کلید رسمی لازم است.

### انتشار نسخه (GitHub Release)

```bash
git tag android-v1.0.0
git push origin android-v1.0.0
```

CI یک Release با APKهای `arm64-v8a` و `armeabi-v7a` (و x86_64) + فایل AAB می‌سازد.
بعد از انتشار، در پنل مدیر کل («اپ اندروید مشتریان» ← تنظیمات و نسخه‌ها) شمارهٔ
`app.latest_version` را به همان نسخه تغییر دهید و در صورت تمایل «به‌روزرسانی اجباری» را روشن کنید.

## اجرای محلی کنار نصب ویندوزی

سامانه روی کامپیوتر دفتر بالا است و گوشی روی Wi‑Fi همان دفتر:

1. APK را نصب و اجرا کنید — در اولین اجرا **آدرس سرور** را می‌پرسد.
2. آدرس کامپیوتر دفتر را بدهید، نمونه: `192.168.1.10:3000`
   (یا QR همان آدرس را اسکن کنید — دکمهٔ اسکن در همان صفحه است).
3. با شماره موبایل و رمز مشتری وارد شوید.

- **امولاتور روی همان کامپیوتر:** آدرس `10.0.2.2:3000` را بزنید.
- تغییر بعدی آدرس: پروفایل ← «آدرس سرور سامانه».
- نسخهٔ ویندوزی به‌صورت پیش‌فرض روی شبکهٔ دفتر (LAN) در دسترس است. اگر فایروال ویندوز
  جلوی اتصال گوشی را گرفت، در **مدیریت سامانه** دکمهٔ «📱 باز کردن فایروال برای موبایل»
  را بزنید (یک قانون باریک فقط برای شبکهٔ خصوصی دفتر می‌سازد)، یا در پنل مدیر کل، بخش
  «اپ اندروید مشتریان» آدرس‌ها و QR آمادهٔ اتصال را ببینید و با گوشی اسکن کنید.

## اعلان‌ها و ورود با اثر انگشت

- اپ برای هر مرحلهٔ تازهٔ پرونده، هر پاسخ کارشناس و هر استوری تازه **نوتیفیکیشن**
  می‌فرستد — برای پرونده‌ها همراه نوار پیشرفت مرحله. این کار بدون فایربیس انجام می‌شود:
  فید اعلان‌های خودِ سامانه هر ۱۵ دقیقه در پس‌زمینه بررسی و در داخل اپ بنر شناور نشان
  داده می‌شود؛ پس روی Wi‑Fi دفتر هم دقیقاً مثل سرور اصلی کار می‌کند.
- خاموش/روشن‌کردن اعلان‌ها و «ورود با اثر انگشت» از پروفایل ← «تنظیمات اپلیکیشن» است.
- روی بعضی گوشی‌ها (شیائومی/سامسونگ) برای دریافت به‌موقع اعلانِ پس‌زمینه، «محدودیت باتری»
  اپ را روی «بدون محدودیت» بگذارید.

## رفتن به سرور اصلی (Production)

فقط اتصال عوض می‌شود؛ هیچ کدی تغییر نمی‌کند:

- **برای هر گوشی:** از پروفایل ← آدرس سرور، دامنهٔ اصلی را بزنید (مثل `https://pishkan.example.ir`).
- **چسباندن آدرس در خود بیلد:** در GitHub از **Settings → Secrets and variables → Actions → Variables**
  متغیر `ANDROID_API_BASE_URL` را با آدرس HTTPS سرور بسازید؛ بیلدهای بعدی همان را پیش‌فرض می‌گیرند
  و صفحهٔ «آدرس سرور» اصلاً دیده نمی‌شود.

محیط‌ها با `--dart-define` از هم جدا هستند:

```bash
flutter run    --dart-define=APP_ENV=local      --dart-define=API_BASE_URL=http://10.0.2.2:3000
flutter build apk --release --split-per-abi \
  --dart-define=APP_ENV=production --dart-define=API_BASE_URL=https://pishkan.example.ir
```

> آدرس دستی کاربر همیشه بر آدرس داخل بیلد اولویت دارد، تا یک APK هم در دفتر (LAN) هم روی سرور اصلی کار کند.
> در Production از HTTPS استفاده کنید؛ اپ برای LAN دفتری HTTP را هم قبول می‌کند (`usesCleartextTraffic`)
> و اگر فقط روی سرور HTTPS کار می‌کنید می‌توانید آن خط را از `AndroidManifest.xml` حذف کنید.

## ساختار

```
apps/mobile/
  android/            اسکلت نیتیو (امضا از key.properties، آیکن انطباقی، RTL)
  assets/fonts/       وزیرمتن (Regular/Medium/Bold)
  ci/                 فایل ورک‌فلوی آمادهٔ کپی در .github/workflows
  lib/
    core/             api (Dio+Bearer)، session (توکن رمزنگاری‌شده)، cache، format (جلالی/پول)، theme
    models/           مدل‌های DTO سازگار با بک‌اند
    services/         فراخوانی‌های API (همان اندپوینت‌های وب + /api/app)
    widgets/          دکمهٔ پلاشی، کارت نرم، فرم داینامیک ۱۳نوعی بک‌اند
    screens/          صفحه‌ها: ورود، داشبورد+استوری، خدمات، ثبت درخواست، پرونده، کیف، پرداخت، چت، تیکت، پروفایل
  test/               تست‌های واحد (اعتبارسنجی‌ها، فرمت، مدل‌ها)
```

نکات رفتاری:

- **قیمت/فرم/مراحل** همه از بک‌اند خوانده می‌شوند؛ تغییر در پنل مدیر بدون نسخهٔ تازه در اپ دیده می‌شود.
- خدمات، دسته‌ها و استوری‌ها **کش آفلاین** دارند؛ عملیات حساس (ثبت نهایی، پرداخت) فقط آنلاین و با تأیید سرور انجام می‌شود.
- پرداخت آنلاین در **مرورگر سیستم** باز می‌شود (امن‌تر و مطابق درگاه‌ها)؛ برگشتن به اپ، پرونده را خودکار تازه می‌کند.
- اعلان‌ها داخل خود اپ + پیامک از زیرساخت موجود سامانه است. پوش واقعی (FCM) نیازمند پروژهٔ Firebase شماست؛
  فیلد `pushToken` در ثبت دستگاه آماده است تا با افزودن `google-services.json` فعالش کنید.
- هیچ کلید محرمانه‌ای داخل اپ نیست؛ توکن نشست در حافظهٔ امن اندروید نگه‌داری می‌شود و روی ۴۰۱ خودکار پاک می‌شود.

## توسعهٔ محلی (اختیاری)

نیازمندی: Flutter پایدار اخیر + JDK 17 + Android SDK

```bash
cd apps/mobile
flutter pub get
flutter analyze && flutter test
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:3000
```
