# استقرار روی سرور از طریق GitHub Actions — راهنمای قدم‌به‌قدم

این راهنما برای کسی نوشته شده که می‌خواهد سامانهٔ **تک پیشخوان** را روی یک VPS
نصب کند، بدون آنکه خودش درگیر دستورات سرور شود. در این روش، عامل هوشمند (یا خودتان)
از طریق GitHub Actions به سرور وصل می‌شود، نصب را اجرا می‌کند و گزارش را می‌خواند.

> **چرا این روش؟** محیط عامل به اینترنت آزاد دسترسی ندارد و نمی‌تواند مستقیم SSH
> بزند؛ اما به مخزن GitHub شما دسترسی دارد. runnerهای گیت‌هاب این پل را می‌سازند:
> از طرف ما اجرا می‌شوند و به سرور شما SSH می‌زنند.

---

## ۰. آنچه لازم دارید

| مورد | توضیح |
| --- | --- |
| VPS | Ubuntu Server **22.04 یا 24.04**، حداقل 1GB RAM و 4GB دیسک آزاد، دسترسی **root** |
| دامنه | اختیاری برای نصب اول؛ برای HTTPS لازم است (رکوردهای A باید به IP سرور اشاره کنند) |
| دسترسی ادمین مخزن | برای افزودن Secrets در GitHub |
| یک نشست SSH فعلی به سرور | فقط برای مرحلهٔ ۱ (ساخت کلید) — مثلاً PuTTY یا ترمینال |

**نکتهٔ امنیتی مهم:** رمز root، کلید خصوصی SSH و هیچ محرمانه‌ای را **در چت نفرستید**.
کلید خصوصی فقط از طریق صفحهٔ Secrets گیت‌هاب (رمزنگاری‌شده) وارد می‌شود.

---

## ۱. ساخت کلید SSH مخصوص استقرار (روی خود سرور)

با همان نشست SSH فعلی‌تان (مثلاً PuTTY) این دستورات را روی سرور اجرا کنید:

```bash
ssh-keygen -t ed25519 -f /root/pishkan_deploy_key -N "" -C "github-actions-deploy"
mkdir -p /root/.ssh && chmod 700 /root/.ssh
cat /root/pishkan_deploy_key.pub >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
cat /root/pishkan_deploy_key
```

خروجی دستور آخر یک کلید خصوصی است که با `-----BEGIN OPENSSH PRIVATE KEY-----`
شروع و با `-----END OPENSSH PRIVATE KEY-----` تمام می‌شود. **تمام آن را کپی کنید**
(همهٔ خط‌ها، شامل BEGIN و END).

> اگر با کاربری غیر از root وصل می‌شوید، مسیرها را با `~/.ssh` همان کاربر جایگزین
> کنید و مطمئن شوید آن کاربر `sudo` بدون رمز دارد (یا از root استفاده کنید).

---

## ۲. افزودن Secrets در GitHub

به مخزن بروید: **Settings → Secrets and variables → Actions → New repository secret**
و این موارد را یکی‌یکی اضافه کنید:

| نام Secret | مقدار | الزامی؟ |
| --- | --- | --- |
| `VPS_HOST` | IP عمومی سرور (مثلاً `203.0.113.10`) | بله |
| `VPS_USER` | کاربر SSH (معمولاً `root`) | بله |
| `VPS_SSH_KEY` | کلید خصوصی کامل که در مرحلهٔ ۱ کپی کردید | بله |
| `VPS_PORT` | پورت SSH (اگر ۲۲ است، لازم نیست) | خیر |
| `VPS_HOST_KEY` | خط known_hosts برای تأیید سخت‌گیرانهٔ هویت سرور (پایین را ببینید) | توصیه می‌شود |

### VPS_HOST_KEY (توصیه‌شده برای امنیت بیشتر)

روی سرور اجرا کنید:

```bash
cat /etc/ssh/ssh_host_ed25519_key.pub
```

خروجی چیزی شبیه `ssh-ed25519 AAAAC3... root@host` است. آن را با **IP سرور و یک فاصله**
در ابتدایش به‌عنوان مقدار `VPS_HOST_KEY` وارد کنید:

```
203.0.113.10 ssh-ed25519 AAAAC3... root@host
```

اگر این Secret را نگذارید، pipeline با `ssh-keyscan` هویت سرور را در اولین اتصال
می‌پذیرد (TOFU) و یک هشدار در لاگ می‌گذارد. برای محیط عملیاتی، گذاشتن آن بهتر است.

### پاک کردن کلید خصوصی از روی سرور (پس از افزودن Secret)

کلید خصوصی دیگر روی سرور لازم نیست؛ فقط کلید عمومی باید در `authorized_keys` بماند:

```bash
shred -u /root/pishkan_deploy_key
```

## ۳. اجرای نصب

1. در مخزن به تب **Actions** بروید.
2. workflow **«Deploy to VPS»** را انتخاب کنید.
3. **Run workflow** را بزنید و ورودی‌ها را پر کنید:

| ورودی | مقدار پیشنهادی |
| --- | --- |
| `action` | `install` |
| `domain` | اگر DNS آماده است دامنه (مثلاً `office.example.ir`)؛ وگرنه **خالی** |
| `acme_email` | ایمیل واقعی برای هشدار انقضای گواهی (وقتی domain پر است، الزامی) |
| `force` | `false` |
| `ref` | خالی (یعنی همان commit که workflow روی آن اجرا می‌شود) |

**دو سناریوی رایج:**

- **دامنه/DNS هنوز آماده نیست:** `domain` را خالی بگذارید. نصب روی IP و HTTP انجام
  می‌شود. بعداً که DNS آماده شد، `action=provision-tls` را با `domain` و `acme_email`
  اجرا کنید تا HTTPS فعال شود.
- **DNS از قبل به سرور اشاره می‌کند:** `domain` و `acme_email` را پر کنید؛ نصب‌کننده
  خودش گواهی Let's Encrypt می‌گیرد و HTTPS را فعال می‌کند.

نصب بسته به سرعت سرور **۵ تا ۱۵ دقیقه** طول می‌کشد (نصب Node.js، PostgreSQL،
nginx، ساخت برنامه و مهاجرت‌ها). پیشرفت را در لاگ زندهٔ workflow می‌بینید.

> نصب‌کننده idempotent است: اگر سرور قبلاً نصب شده باشد، بدون `force=true` چیزی را
> تغییر نمی‌دهد و پیام می‌دهد. داده‌های مشتریان هرگز حذف نمی‌شوند.

---

## ۴. برداشتن رمز اولیهٔ مدیر

رمز اولیهٔ مدیر کل **در لاگ workflow چاپ نمی‌شود**. فقط روی خود سرور در یک فایل
با دسترسی root ذخیره می‌شود. با نشست SSH خودتان:

```bash
sudo cat /etc/pishkan/initial-admin-secret.txt
```

سپس وارد پنل شوید (نام کاربری `admin`)، رمز را عوض کنید و فایل را حذف کنید:

```bash
sudo shred -u /etc/pishkan/initial-admin-secret.txt
```

نشانی پنل: `https://دامنه/admin` (یا `http://IP/admin` اگر هنوز دامنه ندارید).

---

## ۵. فعال‌سازی HTTPS بعد از آماده شدن DNS / Cloudflare

اگر نصب اول IP-only بود، حالا که رکوردهای A (و www) به سرور اشاره می‌کنند:

1. در Cloudflare حالت SSL/TLS را روی **Full (strict)** بگذارید (نه Flexible).
2. در Actions → Deploy to VPS → Run workflow:
   - `action` = `provision-tls`
   - `domain` = دامنهٔ واقعی
   - `acme_email` = ایمیل واقعی
3. اجرا کنید. گواهی گرفته می‌شود، nginx به‌روز می‌شود و HTTP به HTTPS هدایت می‌شود.

---

## ۶. تأیید نهایی

`action=doctor` را اجرا کنید. خروجی باید همه‌چیز را سبز نشان دهد: سرویس، پایگاه
داده، DNS، گواهی TLS و مسیر ACME. اگر موردی قرمز بود، متن آن را به عامل بدهید تا
ریشه‌یابی و اصلاح کند.

سایر عملیات‌ها:

| action | کاربرد |
| --- | --- |
| `status` | وضعیت سریع سرویس، نسخه و آخرین پشتیبان |
| `update` | به‌روزرسانی به commit جدید (با پشتیبان خودکار و بازگشت در خطا) |
| `backup` | پشتیبان‌گیری دستی از پایگاه داده و مدارک |
| `report` | نمایش گزارش نصب (بدون محرمانه) |
| `logs` | خواندن دقیق لاگ‌ها برای عیب‌یابی: وضعیت نشست tmux، خروجی کامل نصب (`deploy-session.log`)، `install.log`، ژورنال مراحل، ژورنال سرویس API و خطای nginx (با حذف خودکار محرمانه‌ها) |
| `reset` | پاک‌سازی نصب نیمه‌کاره/خراب برای نصب دوباره — **نیازمند `force=true`**. فقط کد/سرویس/قفل را برمی‌دارد؛ **دیتابیس، مدارک، تنظیمات و پشتیبان‌ها هرگز حذف نمی‌شوند** |
| `agent` | نشست تشخیصی فقط-خواندنی برای عامل — **نیازمند `request_id` و تأیید شما در پنل سرور** (منوی ۱۳). یک‌بارمصرف، ۱۵ دقیقه‌ای |

### نشست پایدار نصب (tmux) — قطعی SSH نصب را نمی‌کشد

کارهای طولانی (`install`, `update`, `provision-tls`, `backup`) روی سرور داخل یک
**نشست tmux جدا‌شده** به نام `pishkan-deploy` اجرا می‌شوند. یعنی حتی اگر ارتباط
SSH وسط نصب قطع شود (قطعی اینترنت، بسته شدن PuTTY، timeout)، نصب **روی سرور به
کار خود ادامه می‌دهد** و متوقف نمی‌شود. tmux در صورت نبودن، خودکار نصب می‌شود.

**تماشای زندهٔ نصب با PuTTY (هم‌زمان با اجرای عامل):**

1. با PuTTY به سرور وصل شوید (همان IP/پورت/کاربر Secrets).
2. این دستور را بزنید:

   ```bash
   tmux attach -r -t pishkan-deploy
   ```

   پرچم `-r` یعنی **فقط تماشا** — هیچ کلیدی که اشتباهی بزنید به نصب نمی‌رسد.
   اگر بخواهید تعامل هم داشته باشید: `tmux attach -t pishkan-deploy` (بدون `-r`).
3. خروج از تماشا **بدون توقف نصب**: کلید `Ctrl-b` را بزنید، رها کنید، بعد `d`.
4. اگر پیام `no sessions` دیدید یعنی نصب تمام شده (یا هنوز شروع نشده)؛ خروجی
   کامل در `/var/log/pishkan/deploy-session.log` ذخیره شده است:

   ```bash
   tail -n 100 /var/log/pishkan/deploy-session.log
   ```

اگر خودِ اجرای عامل قطع شود، اجرای بعدی همان action به‌جای شروع دوباره، به همان
نشست در حال اجرا وصل می‌شود (resume) و آن را دنبال می‌کند.

### پنل ترمینالی مدیریت (بعد از نصب)

پس از نصب موفق، هر بار با SSH (مثلاً PuTTY) به‌صورت تعاملی وارد سرور شوید، به‌جای
شل خالی، **پنل مدیریت تک پیشخوان** باز می‌شود: وضعیت و سلامت، doctor، لاگ API،
پشتیبان دستی، به‌روزرسانی امن، ری‌استارت، بازنشانی رمز مدیر، **تنظیم دامنه/HTTPS با
ورود مستقیم مقدار**، ویرایش `deploy.conf`، گزارش نصب و بررسی به‌روزرسانی.

- گزینهٔ `0` شما را به شل معمولی می‌برد؛ برای بازگشت `pishkan-panel` را بزنید.
- پنل فقط در ورود **تعاملی SSH** باز می‌شود؛ دستورات خودکار (خودِ workflow، scp،
  cron) اصلاً تحت تأثیر نیستند.
- رد کردن پنل برای یک اتصال: `PISHKAN_NO_PANEL=1` (مثلاً در PuTTY در بخش
  Connection → SSH → Remote command یا به‌صورت `ssh -t root@server 'PISHKAN_NO_PANEL=1 bash -l'`).
- پنل نیاز به کاربر root دارد؛ با کاربر غیر root فقط هشدار می‌گیرید.

### دسترسی تأییدشدهٔ عامل به پنل (هر بار با اجازهٔ شما)

وقتی عامل لازم دارد اطلاعات پنل سرور را بخواند یا با آن کار کند، دسترسی دائمی
ندارد؛ هر نشست یک چرخهٔ تأیید جدا دارد:

1. **عامل درخواست می‌دهد:** یک فایل درخواست در شاخهٔ `pishkan-agent-requests`
   مخزن منتشر می‌کند (شناسه، عملیات، دلیل، انقضا).
2. **شما می‌بینید و تصمیم می‌گیرید:** با PuTTY وارد سرور شوید → پنل مدیریت →
   گزینهٔ **۱۳ «درخواست‌های دسترسی عامل»**. فهرست درخواست‌ها با دلیل هرکدام
   نمایش داده می‌شود. با وارد کردن شناسه و زدن `y` تأیید می‌کنید (یا با `x` لغو).
3. **تأیید محدود است:** فقط عملیات `agent` (تشخیص فقط-خواندنی: status، doctor،
   لاگ‌ها)، فقط **یک بار**، فقط تا **۱۵ دقیقه**. تأیید فقط روی خود سرور ذخیره
   می‌شود؛ عامل هیچ راهی برای تأیید درخواست خودش ندارد.
4. **عامل اجرا می‌کند:** workflow با `action=agent` و `request_id` اجرا می‌شود؛
   سرور تأیید را می‌سنجد و **پیش از اجرا مصرف می‌کند** (حتی اگر اجرا خطا دهد،
   آن تأیید سوخته است). خروجی در گزارش اجرا منتشر می‌شود.
5. **پایان نشست = پایان دسترسی:** برای بار بعد، همین داستان از نو تکرار می‌شود.

> نکته: این دروازه برای نشست‌های تشخیصیِ عامل (`agent`) است. عملیات نصب/به‌روزرسانی
> مثل قبل با تصمیم شما در چت یا دکمهٔ Run workflow اجرا می‌شوند.

### خواندن لاگ توسط عامل (عیب‌یابی خودکار)

هاستِ ذخیرهٔ لاگِ خامِ GitHub Actions از سندباکس عامل قابل دسترسی نیست. برای همین
workflow خروجی کامل هر اجرا را (با حذف IP سرور) به شاخهٔ **`pishkan-deploy-reports`**
منتشر می‌کند (`deploy-reports/run-<شناسه>.log`). عامل آن را از طریق API می‌خواند،
خطا را تشخیص می‌دهد، اصلاح می‌کند و دوباره اجرا می‌کند. اگر نصب نیمه‌کاره ماند،
عامل می‌تواند `logs` را برای تشخیص و در صورت نیاز `reset` (با حفظ همهٔ داده‌ها) را
برای شروع دوباره اجرا کند.

## ۷. عیب‌یابی

| خطا در لاگ | علت رایج | راه‌حل |
| --- | --- | --- |
| `Missing GitHub repository secrets` | Secretها اضافه نشده‌اند | مرحلهٔ ۲ را انجام دهید |
| `Permission denied (publickey)` | کلید در authorized_keys نیست یا اشتباه کپی شده | مرحلهٔ ۱ را تکرار کنید؛ کلید خصوصی کامل (با BEGIN/END) در Secret باشد |
| `Connection refused` / `timed out` | پورت SSH بسته یا فایروال | پورت را در `VPS_PORT` بگذارید؛ فایروال ابر را باز کنید |
| `sudo: a password is required` | کاربر غیر root بدون sudo بی‌رمز | از `VPS_USER=root` استفاده کنید یا NOPASSWD بسازید |
| `ssh-keyscan returned no host keys` | IP/پورت اشتباه | `VPS_HOST` و `VPS_PORT` را بررسی کنید |
| گواهی صادر نشد | DNS منتشر نشده، پورت ۸۰ بسته، یا Cloudflare Flexible | DNS را بررسی کنید؛ پورت ۸۰ باز باشد؛ SSL را Full (strict) کنید؛ بعد `provision-tls` |
| `already installed` | نصب قبلی موفق بوده | برای کد جدید `update`؛ برای اجرای دوبارهٔ نصب‌کننده `force=true` |

## ۸. نکات امنیتی این pipeline

- **کلید خصوصی هرگز در چت یا مخزن نیست.** فقط در Secrets رمزنگاری‌شدهٔ گیت‌هاب.
- گیت‌هاب مقادیر Secret را در لاگ **ماسک** می‌کند؛ اسکریپت هم هیچ محرمانه‌ای چاپ نمی‌کند.
- مخزن public است، پس لاگ workflow عمومی است؛ به همین دلیل گزارش نصب پیش از چاپ
  اسکن می‌شود و اگر الگوی شبیه اعتبارنامه داشت، چاپ نمی‌شود.
- کلید استقرار فقط برای همین کار است؛ برای لغو دسترسی، خط مربوط به
  `github-actions-deploy` را از `/root/.ssh/authorized_keys` حذف کنید.
- نصب‌کننده و `pishkan update` هرگز دادهٔ مشتری را حذف نمی‌کنند؛ update پیش از
  تغییر پشتیبان می‌گیرد و در صورت ناسالم بودن نسخهٔ جدید خودکار بازمی‌گردد.
- هر ورودی (دامنه، ایمیل، SHA، شاخه) پیش از استفاده اعتبارسنجی می‌شود.

---

## ۹. عامل چه می‌کند؟

پس از آنکه Secrets را اضافه کردید و اطلاعات غیرمحرمانه (IP، کاربر، پورت، وضعیت
دامنه) را به عامل دادید، عامل می‌تواند:

1. workflow را اجرا کند. دو راه دارد:
   - **دکمهٔ «Run workflow»** در تب Actions (توسط شما).
   - **`repository_dispatch`** از طریق API (توسط عامل، با رویداد `pishkan-deploy` و
     پارامترها در `client_payload`). GitHub App سندباکس مجوز `workflow_dispatch`
     مستقیم را ندارد (۴۰۳)، اما `repository_dispatch` را دارد؛ برای همین workflow
     هر دو trigger را می‌پذیرد و همان job با همان اعتبارسنجی اجرا می‌شود.
2. لاگ و گزارش نصب را از GitHub بخواند.
3. خطاها را ریشه‌یابی، کد/پیکربندی را اصلاح و دوباره اجرا کند.
4. پس از نصب، `doctor` را اجرا کند تا تأیید نهایی بگیرد.
5. بستهٔ اتصال اندروید (`/etc/pishkan/android-connection.json`) را برای مرحلهٔ بعدی آماده کند.

> اگر فایل workflow شما هنوز فقط `workflow_dispatch` دارد (نسخهٔ اول)، عامل نمی‌تواند
> خودش اجرا کند و باید شما «Run workflow» را بزنید. نسخهٔ به‌روز هر دو trigger را دارد.
