# راهنمای توسعه‌دهنده — چطور آپدیتی بسازیم که بی‌خطر باشد

این سند برای کسی نوشته شده که **بعد از ما** روی پشکان کار می‌کند.

هدف یک چیز است: کاربر فقط `sudo pishkan update` بزند و مطمئن باشد هیچ داده‌ای از دست نمی‌رود، سایت پایین نمی‌آید، و اگر مشکلی پیش آمد برگشت ممکن است.

---

## ۱. قاعدهٔ مرکزی: expand، بعد contract

آپدیت این‌طور کار می‌کند، و این ترتیب قابل تغییر نیست:

```
init → checkout code → npm ci → build
    → migrate          ← 🚨 دیتابیس این‌جا تغییر می‌کند
    → ln -sfn current  ← کد این‌جا عوض می‌شود
    → restart → health check
```

بین `migrate` و `ln -sfn` یک **پنجرهٔ خطر** است. اگر restart شکست بخورد، `rollback` کد را برمی‌گرداند، ولی دیتابیس **تغییرکرده می‌ماند**.

پس قاعده این است:

> **کد قدیمی باید بتواند روی دیتابیس جدید اجرا شود.**

این یعنی هر تغییر دیتابیس در **دو (یا سه) آپدیت** جدا انجام می‌شود:

### &#x2022; آپدیت N — «expand»

فقط چیزهایی که افزودنی هستند:

```sql
ALTER TABLE requests ADD COLUMN priority INT;               -- nullable
CREATE TABLE staff_shifts (...);
CREATE INDEX IF NOT EXISTS idx_x ON y(z);
```

دیتابیس حالا هم با کد قدیمی کار می‌کند، هم با کد جدید.

### &#x2022; آپدیت N+1 — «use»

کد جدید شروع می‌کند به استفادهٔ واقعی. دیگر هیچ‌وقت لازم نیست برگردیم، چون کد قدیمی هم هنوز *کار می‌کند*.

### &#x2022; آپدیت N+2 — «contract»

حالا مجاز است پاک شود — و فقط اگر واقعاً لازم باشد:

```sql
DROP COLUMN old_field;
```

قبل از contract مطمئن شوید هیچ نسخه‌ای در `/opt/pishkan/releases/` که `rollback` می‌تواند به آن برگردد، به آن ستون نیاز ندارد.

---

## ۲. چه چیزهایی ممنوع است در یک آپدیت عادی

### در مهاجرت‌ها

| ممنوع | چرا | به‌جایش |
| --- | --- | --- |
| `DROP TABLE` | برگشت غیرممکن | فاز contract، بعد از دو آپدیت |
| `DROP COLUMN` | همان | همان |
| `RENAME` ستون/جدول | کد قدیمی می‌شکند | ستون تازه + backfill + contract |
| `ALTER COLUMN ... TYPE` | اغلب در SQLite کار نمی‌کند و همیشه برگشت‌ناپذیر است | ستون تازه |
| `DELETE`/`TRUNCATE` روی دادهٔ مشتری | فاجعه | هرگز در مهاجرت |
| دادهٔ نمونه روی تنظیمات واقعی | تنظیمات مدیر را بازنویسی می‌کند | `INSERT ... ON CONFLICT DO NOTHING` |

**تست خودکار:** `bash tools/check_deploy.sh` این‌ها را می‌سنجد و اگر مهاجرتی `DROP`/`RENAME`/`TRUNCATE` داشته باشد، **CI شکست می‌خورد**. این تست را دور نمی‌زنید؛ اگر لازم است چیزی پاک شود، فاز contract در یک PR جدا و با تأیید صریح.

### در کد

- **خواندن ستونی که در همان آپدیت اضافه شده** بدون محافظت `if` — کد ممکن است یک لحظه قبل از migrate اجرا شود.
- **حذف endpoint** که اپ موبایل هنوز از نسخه‌های قدیمی صدا می‌زند. اپ نمی‌تواند هم‌زمان با سرور آپدیت شود.
- **تغییر شکل پاسخ API** (`{data: [...]}` → `[...]`) — اپ قدیمی می‌شکند. یک فیلد جدید اضافه کنید.

---

## ۳. چیزهایی که به `deploy.conf` مربوط می‌شوند

اگر تغییر شما روی **Hostname**، **CORS**، **کوکی** یا **nginx** اثر دارد، این‌ها را رعایت کنید:

1. **نام دامنه را هیچ‌جا hard-code نکنید.** از `deploy.conf` می‌آید.
   ```bash
   # ❌
   APP_URL=https://pishkan.example.ir
   # ✅
   APP_URL="$(config_app_url)"
   ```
2. **اگر فایل قالب nginx را تغییر دادید، بعد از تغییر یک `provision` بزنید** تا مطمئن شوید رندر می‌شود. `check_deploy.sh` این را هم می‌سنجد.
3. **اگر یک بخش دامنهٔ جدید اضافه کردید** (مثل `/shop` که می‌خواهد روی `shop.example.ir` باشد)، الگو این است:
   - یک کلید در `deploy.conf` (`SHOP_MODE`, `SHOP_SUBDOMAIN`)
   - اعتبارسنجی در `config_validate`
   - یک `config_*_subdomain()` که زیردامنه را برمی‌گرداند
   - در `config_cors_origins` و `config_tls_hosts` لحاظ شود
   - بلوک ریدایرکت در `render_site` و `provision_render`
   - یک تست در `check_deploy.sh`

## ۴. چک‌لیست قبل از merge

```bash
bash tools/check_deploy.sh     # منطق استقرار، مهاجرت‌ها، رندر nginx
python3 tools/check_mobile.py  # حدود ۲۰ دروازه: نحوِ Dart، شکلِ فایل‌های Kotlin،
                             # زنجیرهٔ تأیید تحویل، آیکون‌ها، نسخه‌ها
cd apps/api && npx vitest run  # تست‌های API
cd apps/web && npx tsc --noEmit
```

سپس این سؤال‌ها:

- [ ] مهاجرت فقط افزودنی است؟
- [ ] کد جدید اگر روی دیتابیس **قدیمی** اجرا شود، خطا نمی‌دهد؟
- [ ] کد **قدیمی** اگر روی دیتابیس **جدید** اجرا شود، خطا نمی‌دهد؟
- [ ] اپ موبایل نسخهٔ فعلی با این API هنوز کار می‌کند؟
- [ ] اگر این آپدیت وسط کار شکست بخورد، `rollback` واقعاً کار می‌کند؟
- [ ] نام دامنه جایی hard-code نشده؟
- [ ] قالب nginx رندر می‌شود؟ (`check_deploy.sh`)
- [ ] اگر `apps/mobile` دست‌خورده: `flutter analyze` و `compileReleaseKotlin` در **هیچ**
      محیطی جز GitHub Actions اجرا نمی‌شوند (اینجا `dart`/`flutter`/SDK نصب نیست). پس
      `check_mobile.py` را گرفته باشید و بدانید قرمز شدنش یعنی تگ بعدی می‌سوزد.

## ۵. آزمون ارتقای واقعی

قبل از انتشار آپدیت‌های بزرگ، روی یک ماشین مجازی:

```bash
# نصب نسخهٔ قبلی
PISHKAN_COMMIT=<old-sha> sudo -E bash scripts/install.sh

# داده بساز
sudo pishkan seed
# ... چند پرونده، فاکتور، کاربر بساز

# آپدیت
sudo pishkan update --ref <new-sha>

# مقایسه
sudo pishkan doctor
psql -U pishkan -d pishkan -c "SELECT count(*) FROM requests"
```

## ۶. آپدیت‌های بزرگ (major)

بعضی آپدیت‌ها نمی‌شوند اتومات انجام شوند — مثلاً تغییر ساختار پرونده‌ها یا مهاجرت دادهٔ دستی. برای این‌ها:

1. در `CHANGELOG.md` یک بخش `## BREAKING` بنویسید
2. در `docs/UPDATE.md` یک بخش «ارتقای X.Y → X.Z» با مراحل دقیق
3. اگر لازم است کاربر کاری بکند، در خروجی `pishkan update` هم هشدار بدهید

و مهم‌تر: **آپدیت بزرگ را در دو version جدا منتشر کنید.** نسخهٔ اول expand (بی‌خطر، اتومات)، نسخهٔ دوم contract (نیاز به تأیید دستی). این‌طور کسی که یک آپدیت را رد کرده، گیر نمی‌افتد.

---

## ۷. چه چیزی هرگز حذف نمی‌شود

`update`، `rollback` و `migrate` هرگز این‌ها را لمس نمی‌کنند:

- کاربران و حساب مدیر
- پرونده‌ها، فاکتورها، تراکنش‌ها
- تنظیمات (شامل دامنه، پیامک، پرداخت)
- فایل‌های آپلودشده در `/var/lib/pishkan/uploads/`
- کلید رمزنگاری در `pishkan.env`

تنها دستوری که داده را جایگزین می‌کند `pishkan restore` است، و آن هم تأیید تایپی صریح + پشتیبان ایمنی قبل از اجرا می‌خواهد.

اگر تغییری نیاز دارید که یکی از این‌ها را بازنویسی کند، آن دیگر «آپدیت» نیست — یک اسکریپت مهاجرت جدا و مستند است.

## ۸. ساختار نسخه‌ها و آیین انتشار

### قاعدهٔ شماره‌گذاری — تصمیم صاحب سامانه است؛ خودسرانه تغییرش ندهید

```
1.0.<build>          نمونه: 1.0.1217 → 1.0.1218 → 1.0.1219
```

- `<build>` تنها شمارندهٔ زنده است: با هر انتشار **یکی** اضافه می‌شود و بس.
- `1.0` (major/minor) بدون دستور صریح صاحب سامانه حرکت نمی‌کند. هیچ «۲.۰»ای
  از خودتان نسازید، حتی اگر تغییرات بزرگ باشد.
- شماره‌های قبلی در `<build>` جمع می‌شوند: `2.3.5` → `235`، `1.21.7` → `1217`.
  اگر اجزای نسخهٔ چند جزء سامانه با هم نخواند، شمارهٔ انتشار همان بزرگ‌ترین عددِ
  جمع‌شده است (انتشارِ ۱٫۲۱٫۷ اندروید و ۱٫۴٫۰ سامانه شد `1.0.1217`).
- اندروید: `versionName` همان `1.0.<build>` و `versionCode` دقیقاً `<build>`.
  شمارندهٔ جدا (`+80`) حذف شده است؛ دو ساعتِ موازی برای یک انتشار، همان چیزی است
  که این قاعده برای کشتنش نوشته شد.

### شمارهٔ نسخه در ده جا نوشته می‌شود — همه در یک کامیت

| فایل | کلید |
| --- | --- |
| `package.json`، `apps/api/package.json`، `apps/web/package.json` | `"version"` |
| `apps/api/src/env.ts` | مقدار پیش‌فرض `APP_VERSION` |
| `apps/api/src/modules/settings/definitions.ts` | پیش‌فرض `app.latest_version` |
| `apps/web/src/components/shell.tsx` | پیش‌فرض «نسخه …» پایین پنل |
| `apps/mobile/pubspec.yaml` | `version: 1.0.<build>+<build>` |
| `windows/manifest/windows.manifest.json` | `appVersion` و `installerVersion` |
| `windows/lib/ui.ps1` | بازگشتی `Get-PishkanVersion` |

درِ این جدول `python3 tools/checks/version_consistency.py` است و `tools/check_deploy.sh`
هم همان را صدا می‌زند؛ یعنی اگر یک جا جا بیفتد، build و CI رد می‌شوند. دلیلش
تجربه است: `app.latest_version` روی 1.0.0 مانده بود در حالی که اپ 1.4.0 منتشر شده
بود، و تا مدت‌ها هر مشتریِ به‌روز پیام «نسخهٔ تازه موجود است» می‌دید.

### یک انتشار، قدم‌به‌قدم — تا دکمهٔ «به‌روزرسانی» در پنل آن را نصب کند

سرور (و تب به‌روزرسانی پنل) یک چیز می‌خوانند: **تازه‌ترین commitِ شاخه‌ای که در
`deploy.conf` آمده** (پیش‌فرض `main`)؛ و اپ اندروید هم فقط `app.latest_version`
را می‌خواند. هیچ سرویس میانی، هیچ آپلود دستی، هیچ فایلِ کپی‌شده‌ای در این مسیر
نیست — پس «منتشر کردم» یعنی «روی آن شاخه merge شد».

1. کار روی branch خودتان تمام شده و `npm run verify` سبز است.
2. `<build>` را در هر ده جدول بالا بالا ببرید (یک کامیت) و
   `python3 tools/checks/version_consistency.py` را بگیرید.
3. مهاجرت‌ها فقط expand: `apps/api/migrations/NNN_*.sql` باید روی **SQLite و
   PostgreSQL هر دو** اجرا شود (`INTEGER`/`TEXT`، بدون `UPDATE … FROM`). اگر
   ستونی لازم است که به کدِ تازه وابسته است، اول migration، بعد کد — همان بخش ۱.
4. merge به `main` و پوش. از این لحظه روی هر سروری «چیزی برای نصب هست» می‌شود.
5. اگر اپ اندروید تغییر کرده: `git tag android-v1.0.<build> && git push origin --tags`،
   صبر کنید CI ساخت را بسازد و assetها را منتشر کند؛ سپس `app.latest_version` را
   روی همان عدد بگذارید (پیش‌فرض از `definitions.ts` می‌آید، اما روی سرورهای موجود
   **تنظیمات پنل** اولویت دارد و دستی هم‌شماره نمی‌شود — این همان دری است که
   آن پیام کاذب را می‌سازد).
6. روی سرور: تب «به‌روزرسانی سامانه» در پنل ادمین، یا `sudo pishkan update`.
   ترتیب ثابت است: پشتیبان → clone همان یک commit → `npm ci` و build → مهاجرت →
   سوییچ اتمیک `current` → بررسی `/api/health` → در خطا، بازگشت خودکار.
7. تأیید پایانی: `sudo pishkan version` باید همان شمارهٔ تازه را بدهد. (این عدد
   حالا خودکار با سوییچ به‌روز می‌شود؛ قبلاً فقط در نصب اولیه نوشته می‌شد و تا
   ابد همان نصب اول را گزارش می‌کرد.)

### اگر گام «Analyze» در CIِ اندروید قرمز شد

`flutter analyze` تنها جایی است که دارتِ این مخزن واقعاً سنجیده می‌شود: در محیط
توسعهٔ این ریپو نه `dart` هست نه `flutter`، و `tools/check_mobile.py` متنِ فایل‌ها
را می‌خواند نه معناشان. یعنی یک خطای دارت (نام حل‌نشده، import مبهم، امضای غلط)
هیچ علامتی در محلی ندارد و اولین بار همان‌جا می‌ترکد. دو درس از همین گرفته شده:

- **نام‌های هم‌نام با فلاتر نسازید.** `KeepAlive` یک ویجتِ خودِ
  `package:flutter/widgets` است (که `material.dart` هم صادرش می‌کند)؛ کلاسِ پلِ
  اتصال زندهٔ اپ برای همین `KeepAliveLink` نام دارد. هر فایلِ `screens/` که هم
  `material.dart` را import کند و هم یک کلاسِ هم‌نام با فلاتر را، روی هر استفاده
  خطای `ambiguous_import` می‌گیرد. نگهبانش بند آخر
  `tools/checks/dart_delivery_ack.py` است.
- **لاگ را از API هم می‌شود خواند** (برای ابزارک‌ها/ربات‌هایی که صفحهٔ Actions را
  باز نمی‌کنند): شمارهٔ گام‌ها و idِ لاگ از `actions/runs/<run>/jobs`، و آدرسِ
  خامِ لاگ در سَرِ redirectِ `gh api -i repos/<owner>/<repo>/actions/jobs/<job>/logs`
  است. متن خطا با الگوی `error •` جدا می‌شود.

فایل `.github/workflows/android.yml` را از همین محیط **نمی‌شود** عوض کرد: پوش با
این خطا رد می‌شود — `refusing to allow a GitHub App to create or update workflow
… without workflows permission` — و `gh workflow run` هم ۴۰۳ می‌دهد. پس اگر
خواستید گزارشِ analyze مثل بقیهٔ تست‌ها در خلاصهٔ همان check بخوانده شود
(نه فقط در صفحهٔ لاگ)، این گام را خودتان جایگزین `Analyze` کنید و `exit`ِ آخرش
همان کدِ خروجِ `flutter analyze` را نگه می‌دارد:

```bash
set +o pipefail
flutter analyze --no-fatal-infos --no-fatal-warnings 2>&1 | tee "$RUNNER_TEMP/analyze.txt"
code=${PIPESTATUS[0]}
{ echo '#### `flutter analyze`'; echo; echo '```'; tail -n 200 "$RUNNER_TEMP/analyze.txt"; echo '```'; } >> "$GITHUB_STEP_SUMMARY"
exit "$code"
```

و همان‌جا `branches:` را از نامِ یک شاخهٔ کاریِ قدیمی به `arena/**` عوض کنید تا
دارتِ هر شاخهٔ کاری همان‌روز سنجیده شود، نه وقتی که دیر شده و تگ زده‌اید.

### چرا در پنل، نشانی مخزن یا SHA پرسیده نمی‌شود

`REPO_URL`/`REPO_BRANCH` در `deploy.conf` و اعتبارنامه در git config است؛
پنهان و بی‌سؤال می‌ماند، چون پرسیدنش از کسی که پشت مرورگر است یعنی یک غلط
تایپی می‌تواند سرور را به مخزن دیگری وصل کند. مجوزی هم که به کاربر سرویس داده
شده فقط دو دستور با آرگومانِ کامل است:
`pishkan check-update --json` و `pishkan update --json`
(`scripts/lib/update-sudoers.sh`، که `install.sh` و `pishkan provision` آن را
می‌نویسند). چون `--ref` و `--no-backup` در این مجوز نیستند، از پنل **نمی‌شود**
بدون پشتیبان به‌روزرسانی کرد و **نمی‌شود** به یک commit دلخواه پرید؛ انتخاب نسخهٔ
خاص، کارِ آدمِ با root روی خودِ سرور می‌ماند: `sudo pishkan update --ref <SHA-40>`.

### نصب ویندوزی (محیط آزمایش محلی)

پنجرهٔ مدیریت دو دکمهٔ تازه دارد — «بررسی نسخهٔ تازه» (فقط خواندن) و
«به‌روزرسانی سامانه» — و همان‌ها روی خط فرمان:

```bash
node windows/lib/manager.mjs update-check   # چه چیزی نصب است، چه چیزی روی مخزن است
node windows/lib/manager.mjs update         # پشتیبان، بعد انتقال، بعد بررسی سلامت
node windows/lib/manager.mjs update --dry-run true
```

سه تفاوت عمدی با سرور، چون محیط فرق دارد:

- اگر درخت git محلی **تغییر انتقال‌نیافته** داشته باشد، به‌روزرسانی رد می‌شود و
  نام فایل‌ها را می‌گوید. در محیط آزمایش، آن تغییرها معمولاً کارِ همان لحظهٔ
  کسی است که دکمه را زده؛ هیچ بازیابی‌ای نباید آن‌ها را بخورد.
- انتقال فقط `--ff-only` است؛ merge یا rebase محلی نمی‌سازد.
- اگر سرویس پس از سوییچ سالم بالا نیاید، درخت با `git reset --hard` به همان
  commit اول برمی‌گردد — و چون درخت تمیز بوده، این بازگشت چیزی جز کارِ خودِ
  به‌روزرسانی را پاک نمی‌کند.

پشتیبان همان `VACUUM INTO` شناخته‌شدهٔ خودِ مدیر است (نه یک پیاده‌سازی دوم)، و
نشانی مخزن از `git remote origin` خوانده می‌شود؛ برای نصبی که از فایل فشرده
ساخته شده و `.git` ندارد، در `.data/update-source.json` می‌نویسید:
`{ "repo": "…", "branch": "main" }`.

### چه چیزی در نسخهٔ تازه «باید» باشد تا به‌روزرسانی امن بماند

- هیچ مهاجرت مخرب در همان انتشار؛ contract همان ۹۰ روز فرصت دارد (بخش ۲).
- هیچ فایل حذف‌شده‌ای که نسخهٔ **قبلی** به آن نیاز دارد — سوییچ اتمیک است و
  بازگشت باید کار کند.
- اگر `deploy.conf` کلید تازه‌ای لازم دارد، `scripts/lib/config.sh` باید در همان
  کامیت آپدیت شود (بخش ۳)؛ وگرنه provision روی سرور می‌شکند نه روی میز شما.
- اگر nginx/systemd unit عوض می‌شود، `cmd_update` خودش provision را دوباره اجرا
  می‌کند؛ فقط تستش کنید (`bash tools/check_deploy.sh`).

```bash
# نسخه‌های فعلی
sudo pishkan version
sudo pishkan check-update --json   # چه چیزی نصب است و چه چیزی روی مخزن است

# روی سرور
ls -la /opt/pishkan/releases/
readlink /opt/pishkan/current
readlink /opt/pishkan/previous
```

`symlink` تعویض، **اتمیک** است. nginx و systemd هر دو به `/opt/pishkan/current` اشاره می‌کنند، نه به یک مسیر نسخهٔ ثابت. این چیزی است که اجازه می‌دهد سوییچ یک لحظه باشد و برگشت هم همان‌قدر سریع.
