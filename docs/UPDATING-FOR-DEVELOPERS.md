# راهنمای توسعه‌دهنده — چطور آپدیتی بسازیم که بی‌خطر باشد

این سند برای کسی نوشته شده که **بعد از ما** روی پشکان کار می‌کند.

هدف یک چیز است: کاربر فقط `sudo pishkan update` بزند و مطمئن باشد هیچ داده‌ای از دست نمی‌رود، سایت پایین نمی‌آید، و اگر مشکلی پیش آمد برگشت ممکن است.

---

## ۱. قاعدهٔ مرکزی: expand، بعد contract

آپدیت این‌طور کار می‌کند، و این ترتیب قابل تغییر نیست:

```
init → checkout code → npm ci → build
    → migrate          ← 🚨 دیتابیس این‌جا تغییر می‌کند
    → ln -sfn current  ← کد این‌جا عوض می‌شود
    → restart → health check
```

بین `migrate` و `ln -sfn` یک **پنجرهٔ خطر** است. اگر restart شکست بخورد، `rollback` کد را برمی‌گرداند، ولی دیتابیس **تغییرکرده می‌ماند**.

پس قاعده این است:

> **کد قدیمی باید بتواند روی دیتابیس جدید اجرا شود.**

این یعنی هر تغییر دیتابیس در **دو (یا سه) آپدیت** جدا انجام می‌شود:

### &#x2022; آپدیت N — «expand»

فقط چیزهایی که افزودنی هستند:

```sql
ALTER TABLE requests ADD COLUMN priority INT;               -- nullable
CREATE TABLE staff_shifts (...);
CREATE INDEX IF NOT EXISTS idx_x ON y(z);
```

دیتابیس حالا هم با کد قدیمی کار می‌کند، هم با کد جدید.

### &#x2022; آپدیت N+1 — «use»

کد جدید شروع می‌کند به استفادهٔ واقعی. دیگر هیچ‌وقت لازم نیست برگردیم، چون کد قدیمی هم هنوز *کار می‌کند*.

### &#x2022; آپدیت N+2 — «contract»

حالا مجاز است پاک شود — و فقط اگر واقعاً لازم باشد:

```sql
DROP COLUMN old_field;
```

قبل از contract مطمئن شوید هیچ نسخه‌ای در `/opt/pishkan/releases/` که `rollback` می‌تواند به آن برگردد، به آن ستون نیاز ندارد.

---

## ۲. چه چیزهایی ممنوع است در یک آپدیت عادی

### در مهاجرت‌ها

| ممنوع | چرا | به‌جایش |
| --- | --- | --- |
| `DROP TABLE` | برگشت غیرممکن | فاز contract، بعد از دو آپدیت |
| `DROP COLUMN` | همان | همان |
| `RENAME` ستون/جدول | کد قدیمی می‌شکند | ستون تازه + backfill + contract |
| `ALTER COLUMN ... TYPE` | اغلب در SQLite کار نمی‌کند و همیشه برگشت‌ناپذیر است | ستون تازه |
| `DELETE`/`TRUNCATE` روی دادهٔ مشتری | فاجعه | هرگز در مهاجرت |
| دادهٔ نمونه روی تنظیمات واقعی | تنظیمات مدیر را بازنویسی می‌کند | `INSERT ... ON CONFLICT DO NOTHING` |

**تست خودکار:** `bash tools/check_deploy.sh` این‌ها را می‌سنجد و اگر مهاجرتی `DROP`/`RENAME`/`TRUNCATE` داشته باشد، **CI شکست می‌خورد**. این تست را دور نمی‌زنید؛ اگر لازم است چیزی پاک شود، فاز contract در یک PR جدا و با تأیید صریح.

### در کد

- **خواندن ستونی که در همان آپدیت اضافه شده** بدون محافظت `if` — کد ممکن است یک لحظه قبل از migrate اجرا شود.
- **حذف endpoint** که اپ موبایل هنوز از نسخه‌های قدیمی صدا می‌زند. اپ نمی‌تواند هم‌زمان با سرور آپدیت شود.
- **تغییر شکل پاسخ API** (`{data: [...]}` → `[...]`) — اپ قدیمی می‌شکند. یک فیلد جدید اضافه کنید.

## ۳. چیزهایی که به `deploy.conf` مربوط می‌شوند

اگر تغییر شما روی **Hostname**، **CORS**، **کوکی** یا **nginx** اثر دارد، این‌ها را رعایت کنید:

1. **نام دامنه را هیچ‌جا hard-code نکنید.** از `deploy.conf` می‌آید.
   ```bash
   # ❌
   APP_URL=https://pishkan.example.ir
   # ✅
   APP_URL="$(config_app_url)"
   ```
2. **اگر فایل قالب nginx را تغییر دادید، بعد از تغییر یک `provision` بزنید** تا مطمئن شوید رندر می‌شود. `check_deploy.sh` این را هم می‌سنجد.
3. **اگر یک بخش دامنهٔ جدید اضافه کردید** (مثل `/shop` که می‌خواهد روی `shop.example.ir` باشد)، الگو این است:
   - یک کلید در `deploy.conf` (`SHOP_MODE`, `SHOP_SUBDOMAIN`)
   - اعتبارسنجی در `config_validate`
   - یک `config_*_subdomain()` که زیردامنه را برمی‌گرداند
   - در `config_cors_origins` و `config_tls_hosts` لحاظ شود
   - بلوک ریدایرکت در `render_site` و `provision_render`
   - یک تست در `check_deploy.sh`

## ۴. چک‌لیست قبل از merge

```bash
bash tools/check_deploy.sh     # منطق استقرار، مهاجرت‌ها، رندر nginx
python3 tools/check_mobile.py  # نحو و ایمپورت‌های Dart
cd apps/api && npx vitest run  # تست‌های API
cd apps/web && npx tsc --noEmit
```

سپس این سؤال‌ها:

- [ ] مهاجرت فقط افزودنی است؟
- [ ] کد جدید اگر روی دیتابیس **قدیمی** اجرا شود، خطا نمی‌دهد؟
- [ ] کد **قدیمی** اگر روی دیتابیس **جدید** اجرا شود، خطا نمی‌دهد؟
- [ ] اپ موبایل نسخهٔ فعلی با این API هنوز کار می‌کند؟
- [ ] اگر این آپدیت وسط کار شکست بخورد، `rollback` واقعاً کار می‌کند؟
- [ ] نام دامنه جایی hard-code نشده؟
- [ ] قالب nginx رندر می‌شود؟ (`check_deploy.sh`)

## ۵. آزمون ارتقای واقعی

قبل از انتشار آپدیت‌های بزرگ، روی یک ماشین مجازی:

```bash
# نصب نسخهٔ قبلی
PISHKAN_COMMIT=<old-sha> sudo -E bash scripts/install.sh

# داده بساز
sudo pishkan seed
# ... چند پرونده، فاکتور، کاربر بساز

# آپدیت
sudo pishkan update --ref <new-sha>

# مقایسه
sudo pishkan doctor
psql -U pishkan -d pishkan -c "SELECT count(*) FROM requests"
```

## ۶. آپدیت‌های بزرگ (major)

بعضی آپدیت‌ها نمی‌شوند اتومات انجام شوند — مثلاً تغییر ساختار پرونده‌ها یا مهاجرت دادهٔ دستی. برای این‌ها:

1. در `CHANGELOG.md` یک بخش `## BREAKING` بنویسید
2. در `docs/UPDATE.md` یک بخش «ارتقای X.Y → X.Z» با مراحل دقیق
3. اگر لازم است کاربر کاری بکند، در خروجی `pishkan update` هم هشدار بدهید

و مهم‌تر: **آپدیت بزرگ را در دو version جدا منتشر کنید.** نسخهٔ اول expand (بی‌خطر، اتومات)، نسخهٔ دوم contract (نیاز به تأیید دستی). این‌طور کسی که یک آپدیت را رد کرده، گیر نمی‌افتد.

---

## ۷. چه چیزی هرگز حذف نمی‌شود

`update`، `rollback` و `migrate` هرگز این‌ها را لمس نمی‌کنند:

- کاربران و حساب مدیر
- پرونده‌ها، فاکتورها، تراکنش‌ها
- تنظیمات (شامل دامنه، پیامک، پرداخت)
- فایل‌های آپلودشده در `/var/lib/pishkan/uploads/`
- کلید رمزنگاری در `pishkan.env`

تنها دستوری که داده را جایگزین می‌کند `pishkan restore` است، و آن هم تأیید تایپی صریح + پشتیبان ایمنی قبل از اجرا می‌خواهد.

اگر تغییری نیاز دارید که یکی از این‌ها را بازنویسی کند، آن دیگر «آپدیت» نیست — یک اسکریپت مهاجرت جدا و مستند است.

---

## ۸. ساختار نسخه‌ها

```bash
# نسخه‌های فعلی
sudo pishkan version

# روی سرور
ls -la /opt/pishkan/releases/
readlink /opt/pishkan/current
readlink /opt/pishkan/previous
```

`symlink` تعویض، **اتمیک** است. nginx و systemd هر دو به `/opt/pishkan/current` اشاره می‌کنند، نه به یک مسیر نسخهٔ ثابت. این چیزی است که اجازه می‌دهد سوییچ یک لحظه باشد و برگشت هم همان‌قدر سریع.
