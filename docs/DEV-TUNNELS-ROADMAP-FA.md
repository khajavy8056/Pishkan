# نقشهٔ راه: انتشار امن با Microsoft Dev Tunnels

> **وضعیت: فقط بررسی و نقشهٔ راه — هیچ کدی برای این مورد نوشته نشده است.**
> تاریخ بررسی: ۲۰۲۶ · دامنهٔ مطالعه: `devtunnel` CLI، رفتار سرویس ابری مایکروسافت، و
> اثرش روی چهار جای پروژه (نصب‌کنندهٔ ویندوز، سرور API، اپ اندروید، و مدل امنیتی).

---

## ۰. جواب کوتاه

**بله، روی این پروژه کار می‌کند — و حتی از چیزی که فکر می‌کنید ساده‌تر است، چون پروژه
از قبل یک پورت واحد دارد.**

سه دلیل که این روش برای Pishkan «جا می‌افتد»:

1. API خودِ بیلد وب را سرو می‌کند (`apps/web/dist`) و کلاینت وب همهٔ فراخوانی‌ها را با
   مسیر **نسبی** (`/api/...`) می‌زند. یعنی **یک پورت ۳۰۰۰** هم صفحه را می‌دهد هم API را.
   پس یک تونل تک‌پورتی کافی است؛ لازم نیست دو تونل بسازیم.
2. اپ اندروید از قبل صفحهٔ «آدرس سامانه» دارد و `normalizeBaseUrl` هر رشته‌ای را قبول
   می‌کند: `https://xxxx-3000.asse.devtunnels.ms` بدون هیچ تغییری در اپ کار می‌کند.
3. `devtunnel` یک **فایل exe تک‌فایلی** است (`https://aka.ms/TunnelsCliDownload/win-x64`)
   که بدون نصب، بدون Administrator و بدون ری‌استارت، داخل همان پوشهٔ نصب دانلود می‌شود.
   دقیقاً همان الگویی که `ensure-node.ps1` برای Node.js دارد.

**اما سه محدودیت جدی هست** که باید قبل از تصمیم بدانید — بخش ۴ را جای دیگری نخوانید.

## ۱. Dev Tunnels در یک نگاه

| ویژگی | مقدار |
|---|---|
| نصب | `winget install Microsoft.devtunnel` یا دانلود مستقیم exe (بدون نصب) |
| ورود | حساب مایکروسافت / Entra ID / GitHub — **الزامی برای هاست کردن** |
| لینک | `https://<tunnel-id>-<port>.<region>.devtunnels.ms` |
| پورت چندگانه | بله، تا ۱۰ پورت در یک تونل |
| پروتکل | HTTP/HTTPS و WebSocket روی همین لینک؛ TCP خام فقط با `devtunnel connect` |
| ناشناس | با `--allow-anonymous` (پیش‌فرض: خصوصی، فقط خودتان) |
| پایداری لینک | تونل نام‌دار = لینک ثابت بین اجراها |
| سقف رایگان | ۵ گیگابایت در ماه · ۱۰ تونل · ۱٬۵۰۰ درخواست در دقیقه به‌ازای هر پورت · ۲۰ مگابیت بر ثانیه |
| انقضا | تونل موقت با قطع هاست می‌میرد · تونل نام‌دار بعد از **۳۰ روز بی‌استفاده** حذف می‌شود · حداکثر عمر ۳۰ روز که با `update` تمدید می‌شود |
| SLA | ندارد (public preview) — مایکروسافت خودش می‌گوید برای توسعه و آزمون، نه production |

## ۲. آنچه باید در نصب‌کنندهٔ ویندوز اضافه شود

نصب‌کنندهٔ فعلی (`windows\PishkanSetup.cmd` → `scripts\install-windows.ps1`) مراحل
زیر را دارد؛ مرحلهٔ جدید بین «راه‌اندازی سرور» و «گزارش پایان» می‌نشیند.

### ۲.۰ رفتار پیش‌فرض: **اختیاری و خاموش**

دقیقاً مثل تیک «دسترسی موبایل در Wi‑Fi» که الان هست. کاربری که نمی‌خواهد، هیچ چیز
اضافه‌ای نمی‌بیند و هیچ دانلودی هم انجام نمی‌شود.

> ☐ **انتشار روی اینترنت با Microsoft Dev Tunnels** (اختیاری)
> یک لینک عمومی `https://…devtunnels.ms` بساز تا کارفرما از بیرون شبکه ببیند.
> نیازمند ورود با حساب مایکروسافت/گیت‌هاب. فقط برای نمایش و آزمون.

### ۲.۱ دانلود خودکار exe — همان الگوی `ensure-node.ps1`

```
اگر devtunnel در PATH نبود:
  ۱) دانلود https://aka.ms/TunnelsCliDownload/win-x64  →  <root>\windows\bin\devtunnel.exe
  ۲) بررسی موفقیت با  devtunnel.exe --version
  ۳) اگر دانلود نشد: پیام روشن + ادامهٔ نصب بدون تونل (نصب نباید بشکند)
```

نکته‌های اجرایی که باید رعایت شود:
- `-UseBasicParsing` و `[Net.ServicePointManager]::SecurityProtocol = 'Tls12'` برای
  PowerShell 5.1 روی ویندوزهای قدیمی‌تر.
- `aka.ms` ریدایرکت می‌کند؛ باید `-MaximumRedirection` و بررسی حجم فایل (چند ده مگابایت)
  باشد تا یک صفحهٔ HTML به‌جای exe ذخیره نشود.
- فایل در repo **کامیت نمی‌شود**؛ در `.gitignore` بنشیند و همان‌جا بماند (مثل `node_modules`).
- هیچ‌جا به Administrator نیاز ندارد؛ تونل خروجی (outbound) می‌زند، پنجرهٔ فایروال باز
  نمی‌کند.

### ۲.۲ ورود با حساب مایکروسافت

`devtunnel user login` دستگاه را به یک صفحهٔ ورود مایکروسافت می‌فرستد و منتظر می‌ماند.
سه راه، به‌ترتیب پیشنهاد:

1. **پیش‌فرض: ورود تعاملی در پنجرهٔ نصب.** بهترین تجربه؛ کاربر فقط لاگین می‌کند.
2. **جایگزین برای نصب بی‌ناظر (CI/اتوماسیون):** `devtunnel user login -d` (device code) —
   کد را نشان می‌دهد و کاربر در گوشی‌اش وارد می‌کند. مناسب وقتی پنجرهٔ نصب دست کسی نیست.
3. **پیشرفته:** `--access-token` با یک توکن ذخیره‌شده، برای اجرای دوباره بدون لاگین مجدد.

وضعیت ورود در `<root>\windows\.state\tunnel.json` نگه داشته شود (فقط **نام برند/حساب**،
نه توکن) تا نصب‌های بعدی همان حساب را پیشنهاد دهند.

### ۲.۳ ساخت تونل ثابت (نه موقت)

هدف: لینکی که با هر بار ری‌استارت عوض نشود، چون کارفرما آن را در اپ اندروید ذخیره
می‌کند و اگر عوض شود باید دوباره وارد کند.

```
devtunnel create pishkan-office --allow-anonymous --expiration 30d
devtunnel port create  pishkan-office -p <PORT> --protocol http
devtunnel host          pishkan-office     ← همین فرمان، در پس‌زمینه
```

`--allow-anonymous` **الزامی** است، چون کارفرما نه حساب مایکروسافت شما را دارد و نه اپ
اندروید بلد است لاگین مایکروسافت کند. اما هر بار که تونل تمدید می‌شود باید یادآوری باشد
که این لینک عمومی است.

### ۲.۴ خواندن لینک و نوشتنش در پیکربندی

`devtunnel show pishkan-office` خط `Connect via browser:` را چاپ می‌کند. آن مقدار باید:

- در `.env` نوشته شود: `TUNNEL_URL=https://…devtunnels.ms`
- به `APP_URL` و `CORS_ORIGINS` **اضافه** شود، نه جایگزین:
  ```
  CORS_ORIGINS=http://127.0.0.1:3000,http://localhost:3000,https://xxxx-3000.asse.devtunnels.ms
  ```
  (اگر این کار نشود، `originGuard` هر POST از دامنهٔ تونل را رد می‌کند.)
- در گزارش پایان نصب، همراه یک **QR** و یک دکمهٔ «کپی لینک» چاپ شود.

### ۲.۵ اجرای پایدار: تونل باید زنده بماند

`devtunnel host` یک پروسهٔ زنده است. اگر پنجره بسته شود، لینک می‌خوابد. دو گزینه:

- **ساده (پیشنهاد):** همان `manager.mjs` که سرور را بالا می‌آورد، تونل را هم به‌عنوان
  پروسهٔ فرزند بالا بیاورد و در «Pishkan Manager» یک ردیف وضعیت داشته باشد:
  `تونل: فعال — https://…devtunnels.ms  [کپی] [QR] [خاموش/روشن]`
- **پایدارتر (اختیاری، بعداً):** یک Scheduled Task در ویندوز که بعد از ری‌استارت هم
  تونل را بالا بیاورد. (همین حالا هم `Start-Pishkan.cmd` هست؛ می‌شود به آن وصلش کرد.)

### ۲.۶ خاموش‌کردن تمیز

```
devtunnel host  را ببند  →  لینک فوراً می‌خوابد
devtunnel delete pishkan-office  →  در «حذف نصب» موجود
```

## ۳. سه چیزی که **باید** اصلاح شود وگرنه سایت زیر تونل خراب می‌شود

اینها ریسک واقعی‌اند، نه جزئیات. هر سه از کد فعلی خوانده شده‌اند.

### ۳.۱ 🔴 `COOKIE_SECURE=false` + HTTPS = **ورود مدیر ممکن نیست**

نصب‌کنندهٔ ویندوز الان `COOKIE_SECURE=false` می‌نویسد، چون سرور محلی HTTP است. اما
`*.devtunnels.ms` همیشه HTTPS است. کوکی سشن با `sameSite: 'lax'` روی یک سایت HTTPS
با کوکی `secure=false`… در عمل مرورگر مدرن کوکی غیر-secure را روی HTTPS نگه می‌دارد
(مسدود نمی‌کند) **ولی** رفتار مبهم است و با `SameSite` و چند دامنه به‌سرعت شکننده می‌شود.

**نتیجه:** در حالت تونل باید `COOKIE_SECURE=true` نوشته شود. این یک خط در `.env` است،
ولی اگر یادش برود، دقیقاً همان چیزی می‌شود که همه می‌گویند «سایت باز می‌شود ولی نمی‌شود
لاگین کرد». باید در نصب‌کننده، **هنگام فعال‌کردن تونل** خودکار ست شود (و هنگام خاموش
کردن تونل برگردد به `false` تا LAN خراب نشود).

### ۳.۲ 🟠 پروکسی باید بشناسد پشت TLS است

پروژه `TRUST_PROXY=true` دارد و این خوب است. باید مطمئن شویم `X-Forwarded-Proto:
https` را از relay مایکروسافت می‌گیرد تا `req.secure` درست شود و CSP و HSTS درست
انتخاب شوند. **باید در فاز آزمون با یک درخواست واقعی بررسی شود**، چون اگر `req.secure`
غلط باشد، حالت «HTTP» انتخاب می‌شود و `upgrade-insecure-requests` از CSP حذف
می‌ماند — که مشکل امنیتی نمی‌سازد ولی پیام‌های خطای گیج‌کننده می‌دهد.

### ۳.۳ 🟠 صفحهٔ ضدفیشینگ مایکروسافت و اپ اندروید

مایکروسافت برای **اولین بازدید مرورگر** یک صفحهٔ هشدار نشان می‌دهد. طبق مستندات، این
صفحه در این حالت‌ها **پریده می‌شود**:

- متد غیر از `GET` باشد، **یا**
- هدر `Accept` شامل `text/html` نباشد، **یا**
- هدر `X-Tunnel-Skip-AntiPhishing-Page` باشد، **یا**
- هدر `X-Tunnel-Authorization` باشد، **یا**
- کاربر یک بار «ادامه» را زده باشد.

**خبر خوب:** اپ اندروید با Dio و `Accept: application/json` درخواست می‌زند، پس از
همان اول از صفحهٔ هشدار رد می‌شود و مستقیم به API می‌رسد. **پس اپ اندروید نیازی به
هیچ تغییری ندارد.**

**خبر بد:** کارفرمایی که لینک را در **مرورگر گوشی یا کامپیوتر** باز می‌کند، یک بار آن
صفحهٔ «این سایت ممکن است فیشینگ باشد» را می‌بیند و باید «ادامه» بزند. این قابل حذف
نیست (از سمت مایکروسافت است) و **باید از قبل به کارفرما گفته شود**، وگرنه فکر می‌کند
سایت خراب است.

### ۳.۴ 🟡 پیامک/ایمیل و لینک‌های مطلق

اگر برای کارفرما کد ورود پیامکی می‌فرستید، لینک داخل پیامک از `domain.public_url` یا
`APP_URL` ساخته می‌شود. در حالت تونل باید همان `https://…devtunnels.ms` باشد، وگرنه
کارفرما لینکی می‌گیرد که به `127.0.0.1` اشاره می‌کند و از گوشی‌اش باز نمی‌شود.

## ۴. محدودیت‌هایی که باید بدانید (صادقانه)

### ۴.۱ 🔴 **این لینک برای «نمایش» است، نه برای بهره‌برداری**

| ریسک | چرا مهم است |
|---|---|
| **بدون SLA** | سرویس public preview است. برای دموی کارفرما خوب، برای پذیرش واقعی نه. |
| **۵ گیگ در ماه** | اگر چند نفر شروع کنند مدارک آپلود کنند، تمام می‌شود. |
| **۱٬۵۰۰ درخواست در دقیقه** | برای یک دفتر کافی است؛ برای چند کاربر هم‌زمان سنگین، نه. |
| **لینک ثابت اما ۳۰ روزه** | باید تمدید شود، وگرنه حذف می‌شود. |
| **کامپیوتر باید روشن بماند** | برق، اینترنت، خواب ویندوز، به‌روزرسانی ویندوز — همه لینک را می‌خوابانند. |
| **امنیت** | با `--allow-anonymous` هر کسی که لینک را داشته باشد به پنل می‌رسد. **حتماً** روی حساب‌ها رمز قوی و `COOKIE_SECURE=true` باشد. |

**جملهٔ صریح:** برای «کارفرما سایت را ببیند» عالی است. برای «مشتری‌ها واقعاً درخواست
ثبت کنند» از آن استفاده نکنید — برای آن همان سرور واقعی با دامنه و Cloudflare است که
در پروژه از قبل داریم.

### ۴.۲ 🟡 اپ اندروید: لینک، **جای IP و پورت** می‌نشیند

در اپ، جایی که «آدرس سرور» می‌پرسد، کارفرما باید این را وارد کند:

```
https://xxxx-3000.asse.devtunnels.ms
```

**نه** `xxxx.devtunnels.ms:3000`. تابع `normalizeBaseUrl` در اپ هر دو را می‌پذیرد، ولی
فرم درست همان `https://` با پورت پیش‌فرض ۴۴۳ است، چون relay مایکروسافت TLS را
خودش خاتمه می‌دهد.

- `usesCleartextTraffic="true"` در اپ برای حالت لوکال است؛ برای HTTPS لازمی نیست و
  همان‌طور بماند (آسیب ندارد).
- `sameServerOrigin` درست کار می‌کند چون `origin` هر دو یکی است.
- **هیچ تغییر کدی در اپ لازم نیست.** فقط مستندات (`docs/ANDROID-LOCAL-TEST-FA.md`)
  باید یک بخش «اتصال از بیرون شبکه با Dev Tunnel» بگیرد.

### ۴.۳ 🟡 یک چیز که **نمی‌شود**: پورت دیگر روی همان لینک

اگر بعداً خواستید Vite dev server روی ۵۱۷۳ را هم بیرون بدهید، باید پورت دوم در همان
تونل ثبت شود (`devtunnel port create ... -p 5173`). اما در حالت نصب ویندوز اصلاً
لازم نیست، چون همان یک پورت ۳۰۰۰ همه‌چیز را می‌دهد.

## ۵. مراحل اجرا — به‌ترتیب، وقتی تصمیم گرفتید

فازها را جدا نگه داشته‌ام تا بتوانید بعد از دیدن نتیجهٔ هر فاز، فاز بعدی را تأیید کنید.

### فاز ۱ — «هیچ چیز در نصب‌کننده، فقط دستی» (نیم روز)

هدف: **قبل از هر کدنویسی**، ثابت شود تونل روی این پروژه کار می‌کند.

1. `winget install Microsoft.devtunnel` روی ویندوز.
2. `devtunnel user login` و `devtunnel host -p 3000 --allow-anonymous`.
3. سه آزمون که **باید** قبول شوند:
   - باز کردن لینک در مرورگر → صفحهٔ اصلی می‌آید.
   - **ورود مدیر** از همان لینک → اگر کوکی اجازه نداد، یعنی مشکل ۳.۱ را دیده‌ایم.
   - باز کردن `/api/health` از یک کلاینت غیرمرورگر → ۲۰۰.
4. اپ اندروید را روی گوشی با همان لینک وصل کنید (بدون porg).
5. یک آپلود مدرک از گوشی → بررسی رسیدن فایل.

**خروجی فاز ۱: یک گزارش «چه چیزی کار کرد و چه چیزی نشد».** اگر همان‌جا معلوم شد
مشکلی هست که با یک خط `.env` حل نمی‌شود، همین‌جا می‌ایستیم.

### فاز ۲ — دانلود و ورود خودکار در نصب‌کننده (۱ تا ۲ روز)

1. تابع `Ensure-DevTunnel` در `windows\lib\` — دانلود، `--version`، بازگشت روشن.
2. تیک اختیاری در GUI نصب‌کننده + پارامتر معادل در حالت کنسول.
3. `devtunnel user login` تعاملی، و نوشتن وضعیت ورود.
4. ساخت تونل نام‌دار + پورت، و ذخیرهٔ شناسهٔ تونل.
5. نوشتن `TUNNEL_URL` در `.env` + افزودن به `CORS_ORIGINS` (نه جایگزینی).
6. `COOKIE_SECURE=true` فقط در حالت تونل.
7. چاپ لینک + QR در گزارش پایان.

### فاز ۳ — مدیریت در Pishkan Manager (۱ روز)

1. ردیف «تونل» با وضعیت زنده (فعال / خاموش / خطا).
2. دکمه‌های [کپی لینک] [QR] [روشن/خاموش].
3. صفحهٔ «دسترسی موبایل / QR» که هست، آدرس تونل را هم در کنار آدرس LAN نشان دهد.
4. `manager.mjs` پروسهٔ تونل را همراه سرور بالا/پایین ببرد.

### فاز ۴ — مستندات و پیام‌ها (نیم روز)

1. `docs/ANDROID-LOCAL-TEST-FA.md` → بخش «اتصال از بیرون شبکه».
2. یک صفحهٔ کوتاه «راهنمای کارفرما» با سه خط: لینک را باز کن، یک بار «ادامه» بزن،

## ۶. اگر خواستید جایگزین‌ها را هم ببینید

| | Dev Tunnels | Cloudflare Tunnel | ngrok |
|---|---|---|---|
| حساب لازم | مایکروسافت/گیت‌هاب | دامنه روی Cloudflare | ثبت‌نام |
| دامنهٔ اختصاصی | ندارد | **دارد** (دامنهٔ خودتان) | پولی |
| مناسب production | نه | **بله** | نه در رایگان |
| نصب خودکار در ویندوز | exe تک‌فایلی | `cloudflared.exe` تک‌فایلی | exe |
| صفحهٔ هشدار اول | دارد | ندارد | دارد |
| دردسر برای کاربر | کم | متوسط (DNS) | کم |

**نکتهٔ مهم:** چون پروژه از قبل Cloudflare و دامنهٔ واقعی را پشتیبانی می‌کند
(`domain.proxy_provider`, SSL Full strict)، اگر هدف «همیشه آنلاین» است، Cloudflare
Tunnel از Dev Tunnels بهتر است. Dev Tunnels را برای **دمو و نمایش** انتخاب کنید، نه
به‌جای deployment.

## ۷. تصمیم‌هایی که باید بگیرید

1. **حتماً «به‌زودی لینک» یا واقعاً لازم است؟** اگر فقط برای یک دموی کوتاه است، فاز ۱
   کافی است و هیچ کدی نمی‌خواهد.
2. **آیا نصب‌کننده باید تونل را خودکار بالا بیاورد، یا فقط ابزار را نصب کند و راهنما
   بدهد؟** (ساده‌تر و قابل‌اعتمادتر: دومی.)
3. **لینک عمومی (`--allow-anonymous`) یا محافظت‌شده با توکن؟** اگر اپ اندروید باید وصل
   شود، فقط اولی ممکن است — چون اپ هدر تونل نمی‌فرستد.
4. **مبلغ ۵ گیگ در ماه برای کارفرمای شما کافی است؟** اگر قرار است چند نفر مدارک بفرستند،
   نه.
