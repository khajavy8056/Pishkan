# موتور هوشمند تصویر و مدارک — طراحی، سیاست کیفیت و بهره‌برداری

این سند پیاده‌سازی «مدیریت هوشمند تصویر و مدرک مشتری» را توصیف می‌کند: چه کتابخانه‌ای انتخاب شده و چرا،
مسیر پردازش، محل نگهداری نسخه اصلی و نسخه بهینه، سیاست کیفیت، مدل دسترسی، سیاست نگهداری و نتیجهٔ
اندازه‌گیری‌های واقعی.

نسخه: ۲.۰.۰ · مهاجرت مرتبط: `apps/api/migrations/016_media_pipeline.sql` · تاریخ: ۲۰۲۶-۱۰-۳۰

---

## ۱. کتابخانهٔ پردازش و دلیل انتخاب

**`sharp` نسخهٔ `0.35.5`** (موتور libvips) در `apps/api` — تک‌وابستگی بومی و بدون نصب ImageMagick.

| معیار | چرا `sharp` |
| --- | --- |
| پشتیبانی WebP | انکودر WebP با حالت **lossless** و **near-lossless** داخل خود libvips؛ نیازی به ابزار جانبی نیست |
| حفظ ابعاد و رزولوشن | بدون `resize` هیچ نمونه‌برداری انجام نمی‌شود؛ ابعاد نسخهٔ نمایشی = ابعاد اصلی (پیش‌فرض `files.image_max_dimension = 0`) |
| اصلاح چرخش EXIF | `autoOrient`/`rotate()` چرخش را روی پیکسل‌ها اعمال می‌کند و متادیتای گمراه‌کننده حذف می‌شود |
| مصرف حافظه | libvips به‌صورت نواری (streaming) کار می‌کند؛ سقف پیکسل و سقف بُعد در سیاست تعریف شده است |
| متادیتا و سلامت تصویر | `metadata()` و بازخوانی مجدد خروجی برای «تأیید خوانایی» پیش از جایگزینی |
| امنیت | دیکود واقعی فایل؛ فایل جعلی/خراب در همین مرحله رد می‌شود (به‌جای اتکا به پسوند) |

بدیل‌های رد‌شده: `imagemagick` (نیازمند باینری سیستمی و اجرای shell)، `jimp` (جاوااسکریپت خالص، کند و بدون WebP lossless کارا)،
سرویس ابری (نقض الزام «هیچ مدرکی نباید از سرور خارج شود»).

## ۲. مسیر پردازش

```
آپلود کلاینت
   │  multipart → incoming/<random>.part   (multer، سقف حجم از تنظیمات)
   ▼
۱) اعتبارسنجی محتوا  (modules/media/validation.ts)
   • پسوند مجاز؟ (files.allowed_types)
   • امضای واقعی فایل (magic bytes) با پسوند می‌خواند؟
   • PDF: ساختار (Catalog/Pages/Page + trailer/%%EOF) و نبود محتوای فعال (/OpenAction، /JavaScript، Launch)
   • تصویر: دیکود واقعی + سقف پیکسل/بُعد  (inspectImage)
   ▼
۲) ثبت رکورد در DB با وضعیت pending  + آرشیو نسخه اصلی
   • نسخه اصلی دست‌نخورده به private/originals/<fileId>.<ext> منتقل می‌شود (همان بایت‌ها، SHA-256 محاسبه می‌شود)
   ▼
۳) پردازش (modules/media/image.ts → processImage)
   • چرخش EXIF اعمال می‌شود
   • تشخیص «سند بودن» تصویر (نسبت لبه/کنتراست/اشباع) → مسیر سند از فشرده‌سازی افت‌دار ممنوع است
   • کاندیدها به‌ترتیب: WebP lossless → WebP near-lossless (کیفیت‌محور) → WebP lossy (فقط عکس، با دروازه کیفیت)
   • دروازه کیفیت روی رزولوشن اصلی: میانگین اختلاف پیکسل، صدک ۹۹٫۹، نسبت انرژی لبه
   • اگر هیچ کاندیدی هم کوچک‌تر و هم در حد کیفیت نبود ⇒ بایت اصلی سرو می‌شود (بدون بازکدگذاری)
   • پیش‌نمایش ۶۴۰px جداگانه برای فهرست‌ها/چت
   ▼
۴) تأیید و جایگزینی
   • خروجی ابتدا در فایل موقت نوشته و سپس atomic rename می‌شود
   • فقط پس از تأیید خوانایی، storage_key روی نسخه بهینه تنظیم می‌شود
   • شکست پردازش ⇒ processing_status='failed' + پیام فارسی؛ نسخه اصلی همان‌طور سرو می‌شود
   ▼
۵) پاسخ API با متادیتای کامل (ابعاد، حجم اولیه/نهایی، درصد کاهش، وضعیت)
```

پردازش **همگام در مسیر آپلود** انجام می‌شود (بدون صف خارجی): تصاویر مدارک پس از یک‌بار فشرده‌سازی سریع
(میانگین ۲۰۰–۸۰۰ میلی‌ثانیه برای اسکن A4) پاسخ می‌دهند. برای فایل‌های بزرگ‌تر از سقف پیکسل، درخواست پیش از
دیکود رد می‌شود تا RAM محافظت شود. بازیابی پس از کرش در `recoverStuckMedia()` روی بوت انجام می‌شود
(رکوردهای `pending`/`processing` دوباره پردازش می‌شوند).

## ۳. سیاست کیفیت (تغییرناپذیر)

- **مدارک هرگز با فشرده‌سازی افت‌دار ذخیره نمی‌شوند.** مسیر سند فقط lossless یا near-lossless.
- **رزولوشن اصلی حفظ می‌شود**؛ هیچ کوچک‌سازی‌ای روی نسخهٔ اصلی مدارک انجام نمی‌شود.
- **هدف ۷۰–۸۰٪ کاهش حجم، هدف است نه شرط.** اگر با حفظ کیفیت محقق نشود، عدد گزارش می‌شود ولی کیفیت قربانی نمی‌شود.
- **هیچ بازکدگذاری زنجیره‌ای:** نسخه بهینه هرگز ورودی پردازش بعدی نیست؛ ورودی همیشه آرشیو اصلی است.
- **آرشیو اصلی تا تأیید نسخه بهینه حذف نمی‌شود** (و به‌صورت پیش‌فرض هرگز حذف نمی‌شود؛ `files.original_retention_days = 0`).
- دروازه کیفیت (روی رزولوشن اصلی، نه پس از کوچک‌سازی):

| نوع محتوا | میانگین اختلاف پیکسل | صدک ۹۹٫۹ | نسبت حفظ انرژی لبه |
| --- | --- | --- | --- |
| سند (lossless/near-lossless) | ≤ ۱٫۵ | ≤ ۲۴ | ≥ ۰٫۹۸۵ |
| عکس (lossy، تنها حالت مجاز افت‌دار) | ≤ ۲٫۵ | ≤ ۴۰ | ≥ ۰٫۹۰ |

تنظیمات مرتبط (همه در «تنظیمات ← فایل‌ها»):

`files.process_images`، `files.image_quality_mode` (`quality_first` | `lossless_only` | `balanced`)،
`files.image_target_savings_percent`، `files.image_min_savings_percent`، `files.image_lossy_quality`،
`files.image_max_pixels`، `files.image_max_dimension`، `files.preview_max_width`، `files.keep_original_archive`،
`files.original_retention_days`، `files.require_reuse_confirmation`، `files.document_default_validity_days`،
`files.max_size_mb`، `files.allowed_types`.
کلید قدیمی `files.image_max_width` که هرگز اعمال نمی‌شد، با راهنمای «منسوخ» علامت خورده است.

## ۴. محل نگهداری و اتصال به مشتری

```
<UPLOAD_DIR>/                     پیش‌فرض: apps/api/.data/uploads
  incoming/                       فایل موقت آپلود (*.part) — خارج از دسترس HTTP
  private/originals/<fileId>.<ext>  آرشیو امن نسخه اصلی (بایت‌های دست‌نخورده)
  private/optimized/<fileId>.webp   نسخهٔ روزمره (همان چیزی که سرو می‌شود)
  private/previews/<fileId>.webp    پیش‌نمایش ۶۴۰px
  public/                         فقط دارایی‌های عمومی سایت (با مجوز settings.edit)
```

هیچ‌کدام از این مسیرها مستقیماً از وب سرو نمی‌شوند؛ Nginx باید فقط `/uploads/public/` را expose کند.
هر مسیر ذخیره‌سازی از `resolveStoragePath()` عبور می‌کند که `..` و مسیر مطلق را رد می‌کند (ضد path traversal).

جدول‌های افزوده در مهاجرت ۰۱۶:

- `files`: `sha256`, `original_storage_key`, `original_mime`, `original_size`, `width`, `height`, `preview_storage_key`,
  `processing_status` (`pending|processing|ready|skipped|failed`), `processing_mode`, `processing_error`,
  `processing_attempts`, `processing_started_at`, `processed_at`, `quality_score`, `savings_percent`,
  `deduplicated_from`, `document_type`, `linked_customer_id`.
- `customer_documents`: آرشیو مدارک پروفایل مشتری — `doc_type`, `title`, `file_id`, `status`
  (`pending|approved|rejected`), `review_note`, `reviewed_by`, `issued_at`, `expires_at`, `source_request_id`.
- `request_documents`: ستون‌های `customer_document_id`, `document_type`, `expires_at` برای پیوند مدرک پروفایل به پرونده.
- `file_access_logs`: هر خواندن خصوصی (دانلود اصل، پیش‌نمایش، مدرک) با کاربر، IP، زمان و variant.

**نگاشت وضعیت به واژگان درخواستی:** `ready` = پردازش موفق، `skipped` = فرمت نیازمند تبدیل نیست (PDF)،
`failed` = پردازش ناموفق ولی فایل سالم، `pending`/`processing` = در جریان.

یکسان‌سازی محتوا: اگر SHA-256 فایل تکراری باشد، همان پردازش قبلی استفاده می‌شود (`deduplicated_from`) و
دوباره انکود نمی‌شود؛ نسخه اصلی تکراری هم نگه داشته نمی‌شود.

## ۵. قرارداد API

| متد و مسیر | دسترسی | کار |
| --- | --- | --- |
| `POST /api/files/upload?purpose=` | کاربر وارد‌شده | آپلود + اعتبارسنجی + پردازش؛ پاسخ کامل متادیتا |
| `GET /api/files/:id` | مالک، کارشناس پرونده، مدیر | نسخه بهینه (روزمره) |
| `GET /api/files/:id?variant=original` | مالک، کارشناس پرونده، مدیر | آرشیو اصلی؛ در `file_access_logs` ثبت می‌شود |
| `GET /api/files/:id?variant=preview` | همان | پیش‌نمایش سریع |
| `GET /api/files/:id/status` | همان | وضعیت پردازش برای polling |
| `GET /api/files/:id/history` | `documents.view` | تاریخچه دسترسی |
| `POST /api/files/:id/reprocess` | `documents.approve` | پردازش مجدد از روی آرشیو اصلی |
| `DELETE /api/files/:id` | مالک | حذف (اگر به پرونده/مدرک/پیام متصل نباشد) |
| `GET /api/files/meta/limits` | کاربر وارد‌شده | سقف حجم/فرمت برای UI |
| `GET /api/files/media/stats` | `documents.view` | آمار پردازش و صرفه‌جویی |
| `GET /api/files/media/diagnostics` | `documents.view` | بررسی سلامت آرشیوها |
| `POST /api/files/media/prune-originals` | `documents.approve` | پاک‌سازی آرشیو منقضی (`dryRun` پیش‌فرض) |
| `GET /api/documents/types` | عمومی | انواع مدرک + اعتبار پیش‌فرض |
| `GET /api/documents/mine` | مشتری | آرشیو مدارک پروفایل + پوشش انواع |
| `POST /api/documents/mine` | مشتری | ثبت فایل آپلودشده به‌عنوان مدرک پروفایل |
| `POST /api/documents/mine/:id/reuse` | مشتری | استفاده دوباره در پرونده (`confirm: true` الزامی) |
| `DELETE /api/documents/mine/:id` | مشتری | حذف مدرک پروفایل |
| `GET /api/documents/customer/:customerId` | `documents.view` + پروندهٔ ارجاع‌شده | مشاهدهٔ آرشیو مشتری توسط کارشناس |
| `POST /api/documents/:id/review` | `documents.approve` | تأیید/رد مدرک (`decision`, `note`) |
| `GET /api/documents/:id` | مالک/کارشناس دارای پرونده/مدیر | جزئیات مدرک |

پیوست پرونده پذیرای دو شکل است: `{ fileId }` (فایل تازه) یا `{ customerDocumentId, confirmReuse: true }`
(استفاده دوباره از مدرک پروفایل). استفاده دوبارهٔ مدرک **ردشده** یا **منقضی** رد می‌شود و
«تأیید بدون کلیک» ممکن نیست.

## ۶. کنترل‌های امنیتی

- اعتبارسنجی سه‌لایه: پسوند مجاز → امضای واقعی (magic bytes) → دیکود واقعی/sanity تصویر و ساختار PDF.
- رد PDF با `/OpenAction`، `/JavaScript`، `/Launch` (جلوگیری از فایل فعال).
- نام نمایشی امن (`safeDisplayName`)؛ نام فیزیکی همیشه `<fileId>.<ext>` تولیدشده توسط سرور — نام اصلی کاربر هرگز در مسیر نمی‌آید.
- سقف حجم (multer)، سقف پیکسل و بُعد (پیش از دیکود) — محافظ RAM/CPU.
- هیچ مسیر خصوصی از وب سرو نمی‌شود؛ دسترسی فقط از `GET /api/files/:id` با `requireAuth` و بررسی رابطه
  (مالک، کارشناس ارجاع‌شده، مدیر کل)؛ `?variant=original` نیز همان کنترل را دارد.
- ثبت هر دسترسی خصوصی در `file_access_logs`؛ در لاگ‌ها فقط شناسه، بدون محتوا یا داده حساس.
- حذف امن: ابتدا رکورد و پیوندها، سپس فایل؛ آرشیو اصلی قبل از تأیید نسخه بهینه حذف نمی‌شود.
- `files.retention_days` و `files.original_retention_days` سیاست نگهداری را مشخص می‌کنند؛ پاک‌سازی فقط با
  اجرای دستی مدیر (`prune-originals`) و به‌صورت `dryRun` پیش‌فرض انجام می‌شود.


پاک‌سازی آزمایشی (dry-run) را نشان می‌دهد.

## ۸. محدودیت‌های شناخته‌شده

- پردازش همگام است؛ برای آپلود انبوه (چند ده مدرک هم‌زمان) بهتر است صف پایدار اضافه شود. API فعلی
  هم‌زمانی را با محدودیت نرخ و سقف پیکسل مدیریت می‌کند، ولی صف اولویت‌دار ندارد.
- PDF تبدیل نمی‌شود (فقط اعتبارسنجی و آرشیو)؛ بهینه‌سازی PDF نیازمند کتابخانهٔ دیگر و بازبینی کیفیت است.
- HEIC/HEIF دیکود نمی‌شود؛ در تنظیمات مجاز هم نیست تا خطای کاربر ایجاد نشود.
- اندازه‌گیری‌ها روی نمونه‌های مصنوعی و در محیط CI با SQLite انجام شده؛ آزمون با فایل‌های واقعی مشتری
  و روی PostgreSQL هنوز در دستور کار است.
