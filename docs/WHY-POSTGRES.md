# چرا سرور روی PostgreSQL است و نه SQLite

این سند به یک سؤال مشخص جواب می‌دهد: «همه‌چیز روی ویندوز با SQLite کار می‌کند؛ چرا روی سرور هم
از همان استفاده نکنیم؟» جواب با عدد و با کدی که در همین مخزن اجرا شد نوشته شده، نه با حدس.

## خلاصه

**می‌شود.** SQLite روی سرور یک تک‌فرآیند هم‌زمان هم کاملاً پایدار اجرا می‌شود؛ آزمایش زیر این را
نشان می‌دهد. اما سه دلیل واقعی وجود دارد که چرا PostgreSQL انتخاب شده — و **هیچ‌کدام سرعت نیست**.
اندازه‌گیری روی همین پروژه نشان داد SQLite روی بار واقعی حتی تندتر است:

1. **`node:sqlite` هنوز experimental است** — خود Node در هر اجرا هشدار می‌دهد:
   `ExperimentalWarning: SQLite is an experimental feature and might change at any time`.
   یک API آزمایشی، پایهٔ دادهٔ کسب‌وکار نیست: امضای توابع و رفتارش بین نسخه‌های Node می‌تواند
   عوض شود و ارتقای Node به یک پروژهٔ مهاجرت تبدیل می‌شود.
2. **پشتیبان‌گیری، بازیابی و انتقال** — `pg_dump`/`pg_restore` ابزار رسمی، نسخه‌بندی‌شده و
   تست‌شده‌اند. نسخهٔ SQLite یک کپی فایل است؛ همان سادگی، باگ «بازیابی بی‌صدا» را ساخت
   (پایین ببینید) و همان است که انتقال بین دو ماشین را شکننده می‌کند.
3. **رشد آینده** — اگر دفتر روزی چند کاربر هم‌زمان با گزارش‌های سنگین داشته باشد، خاصیت همگام
   بودن درایور به سقف می‌خورد. امروز این سقف دور است، ولی انتخاب موتور برای سال آینده انجام
   می‌شود نه برای امروز.

**مهم‌تر از انتخاب موتور، این است که کد روی هر دو یکی رفتار کند** — و تا امروز این‌طور نبود.
پنج باگ واقعی پیدا و رفع شد که همه‌شان روی SQLite پنهان بودند و روی سرور خراب می‌کردند.

## اندازه‌گیری‌ها

هر عدد روی همین مخزن، با ۲۰٬۰۰۰ رکورد و همان کوئری تجمیعی که داشبورد استفاده می‌کند.

> **هشدار روش‌شناسی — این بخش قبلاً عدد گمراه‌کننده داشت و اصلاح شد.**
> دو عدد زیر روی یک جدول مصنوعی ۲۰٬۰۰۰ رکوردی گرفته شده‌اند، نه روی بار واقعی این پروژه.
> اندازه‌گیری روی همان دیتابیس واقعی (۱۹۳ خدمت، همان endpoint داشبورد) نتیجهٔ **برعکس** داد:
> SQLite تندتر بود. جدول دوم را ببینید.

### آزمون مصنوعی (۲۰٬۰۰۰ رکورد) — فقط اثر «قفل شدن event loop» را نشان می‌دهد

| سنجه | SQLite (`node:sqlite`) | PostgreSQL |
| --- | --- | --- |
| یک کوئری تجمیعی | ۴.۴ ms | ۳.۲ ms |
| ۳۰ کوئری هم‌زمان | ۹۲.۷ ms | ۶۶ ms |
| حداکثر توقف event loop | ۸۹ ms | ۷ ms |

توقف event loop یعنی: در آن ۸۹ میلی‌ثانیه هیچ درخواست HTTP دیگری پاسخ نمی‌گیرد — نه صفحهٔ
مشتری، نه تأیید پرداخت، نه درخواست اپ اندروید. این ویژگی **واقعی** است: درایور SQLite در Node
همگام است. ولی اندازهٔ آن به حجم کوئری بسته است، و در بار واقعی این پروژه کوچک است (زیر).

### آزمون روی بار واقعی — همین پروژه، سرور واقعی، هر دو موتور

`GET /api/dashboard/summary` با همان داده و همان سرور:

| سنجه | SQLite | PostgreSQL |
| --- | --- | --- |
| تک درخواست | **۵.۶ ms** | ۳۸.۱ ms |
| ۲۰ درخواست هم‌زمان | **۲۰.۹ ms** | ۲۹۱.۶ ms |
| `GET /api/public/services` با ۵۰ درخواست هم‌زمان (p95) | **۱۵۵.۷ ms** | ۱۶۴.۸ ms |

`GET /api/public/services` تقریباً برابر است (تفاوت در حد نوسان). داشبورد روی SQLite **چند برابر
تندتر** است.

### نتیجهٔ صادقانه

**«SQLite روی سرور کند است» برای این پروژه درست نیست.** روی حجم دادهٔ یک دفتر پیشخوان، SQLite
سریع‌تر یا هم‌سرعت است. کسی که با استدلال سرعت PostgreSQL را انتخاب کند، برای این پروژه اشتباه
می‌کند. دلایل واقعی در بخش بعد آمده‌اند و به سرعت مربوط نیستند.

### آنچه *مشکل نیست*

- **نوشتن هم‌زمان:** ۶ فرآیند جداگانه، هر کدام ۴۰ تراکنش `BEGIN IMMEDIATE` → **۲۴۰ از ۲۴۰ موفق،
  صفر خطای `SQLITE_BUSY`** (با `busy_timeout`). SQLite زیر این حجم پایدار است.
- **چندین worker:** سرویس با یک فرآیند (`Type=simple`) اجرا می‌شود، پس سناریوی «چند نویسنده»
  اصلاً پیش نمی‌آید.

پس استدلال درست این نیست که «SQLite زیر بار می‌شکند» — این اغراق است. استدلال درست این است که
SQLite تأخیر را به **همه** منتقل می‌کند، و درایورش در Node هنوز آزمایشی است.

## پنج باگ پیدا شده — همه روی SQLite پنهان، همه روی سرور خراب

این‌ها فرضی نیستند؛ همه با اجرای همان مجموعهٔ تست روی یک PostgreSQL واقعی (نسخهٔ ۱۶.۲) پیدا شدند.

### ۱. `SUM(boolean)` — خطای ۵۰۰ روی صفحهٔ آمار اپ

```sql
-- SQLite: مقایسه مقدار 0/1 برمی‌گرداند، پس SUM کار می‌کند
-- PostgreSQL: نوع boolean واقعی است و sum(boolean) وجود ندارد
SELECT SUM(status = 'published') FROM app_banners
```

نتیجه در تولید: `GET /api/app/admin/stats` → **۵۰۰ Internal Server Error**.
رفع: `SUM(CASE WHEN status = 'published' THEN 1 ELSE 0 END)`.

### ۲. پارامتر اعشاری داخل `SUM` — خطای ۵۰۰ روی «ثبت درخواست»

```sql
SUM(CASE WHEN work_bucket IN (...) THEN ? ELSE 1 END)   -- پارامتر = 0.25
```

PostgreSQL نوع پارامتر را از `ELSE 1` (عدد صحیح) استنتاج می‌کند و `"0.25"` را با
`invalid input syntax for type integer` رد می‌کند. نتیجه: **ثبت درخواست مشتری ۵۰۰ می‌شد** —
یعنی مهم‌ترین مسیر کسب‌وکار.

### ۳. مرگ تراکنش پس از یک خطای غیرکشنده (خطرناک‌ترین)

در PostgreSQL اگر یک دستور داخل تراکنش شکست بخورد، **کل تراکنش تا `ROLLBACK` غیرفعال** می‌شود:
`current transaction is aborted, commands ignored until end of transaction block`.
SQLite بعد از خطا به کار ادامه می‌دهد.

کد ما عمداً چند کار «best-effort» را می‌بلعد — `writeAudit` («هرگز به مسیر درخواست پرتاب نکن») و
`logEvent`. روی SQLite بی‌ضرر بود. روی PostgreSQL یک خطای ثبت audit باعث می‌شد درخواستی که
**موفق شده بود**، در خواندن بعدی با ۵۰۰ بیفتد. دقیقاً الگوی «روی لوکال کار می‌کند، روی سرور نه».

رفع: یک `txSavepoint()` واقعی در لایهٔ داده (`SAVEPOINT` / `ROLLBACK TO`) و استفاده از آن در
`writeAudit` و `logEvent`. حالا رفتار روی هر دو موتور **صریحاً** یکسان است.

### ۴. `COUNT(*)` رشته برمی‌گردد، نه عدد

PostgreSQL هر `bigint` (شامل `COUNT(*)` و `SUM(integer)`) را **رشته** برمی‌گرداند تا ۶۴ بیت از
دقت کم نشود؛ SQLite عدد برمی‌گرداند. نتیجه: `count + 1` می‌شد `"11"`، مقایسه‌ها رد می‌شد و شکل
پاسخ JSON بین ویندوز و سرور فرق می‌کرد.

رفع: نوع‌های `int8` و `numeric` در درایور به `number` نگاشت شدند. همهٔ مقادیر produced شده در این
برنامه شمارش ردیف، مبلغ ریالی یا مدت‌زمان‌اند — همه زیر `Number.MAX_SAFE_INTEGER`، پس تبدیل
بدون افت است.

### ۵. بازیابی بی‌صدا — بکاپ ویندوز روی سرور «موفق» می‌شد و داده‌ای نمی‌آمد

این بدترین بود. در `pishkan restore`، اگر فایل پشتیبان `database.sqlite` داشت — یعنی هر بکاپی که
از نسخهٔ ویندوزی گرفته شده — همان فایل روی دیسک کپی می‌شد، **حتی وقتی سرور روی PostgreSQL است**:

```bash
cp "${workdir}/database.sqlite" "$SQLITE_TARGET"   # ← سرور اصلاً این فایل را نمی‌خواند
```

سرویس بالا می‌آمد، `DB_DRIVER=postgres` بود، و **همهٔ جدول‌ها خالی**. بدون هیچ خطایی.
رفع: گارد صریح که جلوی بازیابی SQLite روی سرور Postgres را می‌گیرد و به مسیر درست
(`pishkan migrate-sqlite`) راهنمایی می‌کند.

## سرور و ویندوز باید یکی باشند — و همین کار شد

تا امروز مجموعهٔ تست **همیشه** روی SQLite اجرا می‌شد، چون `vitest.config.ts` مقدار
`DB_DRIVER: 'sqlite'` را هاردکد کرده بود و `test.env` متغیرهای پوسته را بازنویسی می‌کرد. یعنی
PostgreSQL — تنها موتوری که در تولید استفاده می‌شود — **هرگز در هیچ تستی اجرا نشده بود**. همین
«کور بودن» پنج باگ بالا را پنهان کرده بود.

تغییرات:

- `vitest.config.ts` موتور را از `PISHKAN_TEST_DB` می‌خواند؛
- `tests/helpers.ts` برای PostgreSQL اسکیمای `public` را از نو می‌سازد (SQLite فایل تازه می‌گیرد)؛
- `tests/sql-dialect.test.ts` هر پنج کلاس باگ را به‌عنوان گارد دائمی می‌پاید.

**نتیجهٔ نهایی، روی همین مخزن:**

| موتور | نتیجه |
| --- | --- |
| SQLite | **۵۰ / ۵۰ فایل سبز** |
| PostgreSQL 16.2 | **۴۸ فایل سبز، ۲ فایل skip** (تست‌های ذاتاً SQLite) |

از این پس هر کدی که فقط روی یکی از دو موتور کار کند، به‌جای تحویل روی سرور، همین‌جا قرمز می‌شود.

## توصیه (تصمیم گرفته‌شده)

| گزینه | وضعیت |
| --- | --- |
| ویندوز طراحی: SQLite | **بله — انتخاب شد** |
| سرور تولید: PostgreSQL | **بله** |
| ویندوز طراحی: PostgreSQL | ممکن است، ولی انجام نمی‌شود |

**دلیل تصمیم:** نصب ویندوزی با SQLite کار می‌کند و پایدار است. ابزارهای خود ویندوز
(`manager.mjs` برای بکاپ و بازیابی، `verify.mjs`، `installer.mjs`، `selftest.mjs`) مستقیماً با
فایل `.sqlite` کار می‌کنند و تغییرشان ریسک دارد. در مقابل، ریسک واقعی «اختلاف لوکال و سرور» با
راه دیگری برداشته شد: تست‌ها روی **هر دو** موتور اجرا می‌شوند و کدی که فقط روی یکی درست باشد
قرمز می‌شود. پس ویندوز دست‌نخورده می‌ماند و امنیت انتقال از جای دیگری می‌آید.

اگر روزی این تصمیم عوض شد، فهرست کارها این است (برای برآورد، نه اجرا):

| فایل | تغییر لازم |
| --- | --- |
| `windows/lib/manager.mjs` | بکاپ با `VACUUM INTO` → `pg_dump`؛ بازیابی با کپی فایل → `pg_restore` |
| `windows/lib/installer.mjs` | نوشتن `DATABASE_URL` به‌جای `SQLITE_FILE`؛ بررسی سلامت با `PRAGMA quick_check` → اتصال به سرور |
| `windows/lib/verify.mjs` | چک وجود فایل دیتابیس → چک اتصال به سرور |
| `windows/lib/selftest.mjs` | ۱۰ assertion روی `DB_DRIVER=sqlite` باید دوحالته شود |
| `install-windows.ps1` | مسیر قدیمی؛ اگر باز هم پشتیبانی می‌شود، همان تغییر |

## انتقال از ویندوز (SQLite) به سرور (PostgreSQL)

این تنها مسیر پشتیبانی‌شده است و **کپی پوشه نیست**:

1. روی ویندوز از پنل مدیر یک «بکاپ کامل» بگیر (شامل پایگاه داده + آرشیو مدارک)؛
2. فایل بکاپ را به سرور منتقل کن؛
3. `pishkan restore <file>` روی سرور.

`pishkan restore` اگر بکاپ SQLite را روی سرور PostgreSQL ببیند **رد می‌کند** و پیام می‌دهد —
این گارد عمداً وجود دارد؛ قبلاً همان فایل را کپی می‌کرد و «موفق» اعلام می‌کرد در حالی که همهٔ
جدول‌ها خالی بودند.

> نکتهٔ باز: بکاپ فعلی `APP_ENCRYPTION_KEY` را همراه ندارد. بدون آن، تنظیمات رمزشده و
> `users.mfa_secret` روی سرور باز نمی‌شوند. تا وقتی این رفع نشده، کلید را جداگانه و امن نگه دار.

## مرجع اجرا

```bash
# SQLite (پیش‌فرض توسعه)
cd apps/api && npx vitest run

# PostgreSQL — همان مجموعه، دقیقاً همان انتظارات
PISHKAN_TEST_DB=postgres \
DATABASE_URL="postgres://user:pass@127.0.0.1:5432/pishkan_test" \
  npx vitest run
```
