# نقش‌ها، کارتابل و رابط RTL — افزودهٔ ۲۰۲۶-۱۰-۲۷

## ورود مشترک و پنل مبتنی بر نقش

کارکنان، حسابدار، مدیر داخلی و مدیر کل از همان `/login?account=staff` و همان API `POST /api/auth/login` استفاده می‌کنند؛ جداگانه بودن دکمه «ورود کارکنان و مدیران» در صفحه خانه یک انتخابگر مجزای احراز هویت یا درگاه دوم نیست. نوع و نقش معتبر از نشست سرور می‌آیند. پس از ورود، `homeFor` حسابدار را به `/staff/accounting`، کارمند را به `/staff` و مدیر را به `/admin` می‌برد. مدیرِ دارای `kind=admin` و نقش‌های manager/super_admin به پنل مدیریت می‌رود؛ مجوزهای خود را همچنان جداگانه کنترل می‌کند.

| نقش پایه | میزکار | حسابداری | تنظیمات/زیرساخت | پرونده مشتری |
|---|---|---|---|---|
| کارمند اجرایی / بازبین | پرونده‌های تخصیص‌یافته، مدارک، گفتگو، صفِ مجاز | ممنوع | ممنوع | فقط پرونده تخصیص‌یافته؛ دیدن/بارگذاری مدرک بر مبنای مجوز |
| حسابدار | کارتابل مالی، حسابداری، گزارش و تسویه فقط با مجوز نقش | مجاز برای فاکتور/پرداخت/هزینه طبق مجوز | ممنوع | تنها حد مورد نیاز نقش؛ دسترسی خودکار به مدارک نتیجه خصوصی نیست |
| مدیر داخلی / سرپرست | پنل مدیریت، عملیات، کارکنان، ساخت/ویرایش خدمت، گزارش و تصمیم‌ها طبق نقش | طبق مجوزهای خود | تنظیمات/زیرساخت حساس ممنوع | محدوده دفتر، همراه audit |
| مدیر کل | همه منوها و عملیات مصرح، از جمله تنظیمات و زیرساخت | مجاز | مجاز | محدوده کامل |

منوی Sidebar برای roleCode فیلتر می‌شود؛ guard رابط صرفاً UX است. API همچنان `requirePermission`، `officeScope` و کنترل مالکیت پرونده را جداگانه اجرا می‌کند. کارمند در خواست تغییر تنظیمات/ایجاد پرسنل/ایجاد خدمت/فاکتورهای همه دفتر در browser smoke و API test با 403 رد شده است. برای حسابداری و مدیر کل هم آزمون واقعی API اجرا شده است.

## گردش کار پرونده و تحویل نتیجه

مهاجرت افزایشی `008_case_automation.sql` جدول append-only عملیاتی ارجاع، status و تصمیم مدیریت/حسابداری می‌سازد؛ migrationهای قبلی و سوابق پرونده حذف یا بازنویسی نمی‌شوند.

1. کارمند باید پرونده تخصیص‌یافته و مجوز `requests.edit` داشته باشد.
2. در «تحویل نتیجه» حداکثر ۱۰ PDF/تصویر در فضای خصوصی upload می‌کند، سپس فایل/علت در تراکنش به پرونده پیوست می‌شود. فایلِ متعلق به کاربر دیگر، پرونده دیگر یا ارسال تکراری رد می‌شود.
3. پرونده وارد `under_review` می‌شود؛ ارجاع مدیریت، event غیرقابل‌مشاهده مشتری و اعلان ایجاد می‌شود.
4. کارتابل هر واحد بر مبنای roleCode *و* مجوز تصمیم جداست؛ کارمند ساده، حسابدار روی ارجاع مدیریت و مدیر بی‌مجوز مالی نمی‌توانند تصمیم واحد دیگر را ثبت کنند.
5. تصمیم تکراری با شرط `status='pending'` رد می‌شود. برگشت برای اصلاح پرونده را به `in_progress` برمی‌گرداند. هنگام تأیید مدیریت فقط خروجی‌های کارمند pending به approved می‌رسند.
6. مدرک staff برای مشتری در JSON پرونده و دانلود private file مخفی است تا تأیید مدیریت. فایل مشتری نیز برای کارمند به مجوز `documents.view` و پرونده تخصیص‌یافته محدود می‌شود.
7. ارجاع باز مدیریت/حسابداری و فایل خروجیِ تأییدنشده مانع `ready/completed` است. ارجاع مالی، خودکار پرداخت دریافت یا هزینه مالی ثبت نمی‌کند؛ حسابدار باید تراکنش واقعی را در بخش حسابداری ثبت/تأیید کند. دکمه‌های تغییر status نیز در رابط براساس وضعیت مجاز سرور و مجوز تأیید پالایش می‌شوند.

ثبت علت ارجاع به حسابداری یا مدیریت فعلاً انتخاب صریح کارکنان/مسئول پرونده است؛ تشخیص خودکار نوع خدمت، SLA/تشدید زمان‌دار، امضای دیجیتال، تفکیک دفتر در tenantهای مستقل و اتصال به سیستم بیرونی حسابداری در این افزوده پیاده نشده است. گردش جایگزین روند پرداخت و کنترل‌های مالی سایر نقاط سامانه نیست.

### endpointهای جدید

- `POST /api/requests/:id/deliver` — `{files:[{fileId,title}],summary}`
- `POST /api/requests/:id/handoffs` — `{department:'management'|'accounting',reason}`
- `GET /api/requests/:id/handoffs`
- `GET /api/automation/inbox`
- `POST /api/automation/:id/decision` — `{decision:'approved'|'returned',note}`
- مسیرهای فوق در namespace `/api/v1` هم موجودند.

## رابط مطابق تصاویر مرجع

- صفحهٔ ورود پرسنل/مدیران مشترک با تعیین پروفایل پس از احراز هویت.
- Home با رنگ آبی سازمانی، نوار ناوبری رسمی، کارت ورود نقش‌محور، جست‌وجوی backend، کاتالوگ و اطلاعیهٔ روشن درباره نمونه‌بودن تعرفه‌ها.
- Sidebar سرمه‌ای ثابت در دسکتاپ، منو و Dock چهار/پنج‌گزینه‌ای پایین صفحه در موبایل، رنگ آبی قابل‌مشاهده برای بخش فعال.
- فرم‌های برچسب‌دار متصل به input و پیام خطا/required قابل‌دسترس؛ فونت محلی Vazirmatn و ریسپانسیو.
- تصویر Hero تولیدشده صرفاً تزیینی و در خود Home به عنوان تصویر واقعی دفتر معرفی نمی‌شود.

## بازآزمایی این افزوده

در این تغییر:

- `npm test`: **۶۷ API + ۱۴ وب** گذشت؛ `automation.test.ts` هشت آزمون API جدید دارد.
- ممیزی acceptance مستقل: **۱۶/۱۶**.
- `npm run typecheck`, `npm run build`، `npm audit --audit-level=high`: موفق؛ صفر advisory گزارش‌شده.
- آزمون e2e با Chromium واقعی: صفحهٔ خانه و پنل مدیر، login یکسان مدیر/حسابدار/کارمند، روتینگ حسابداری و حقوق، رد تنظیمات از حسابدار، رد حسابداری از کارمند و Dock/بدون overflow در viewport موبایل **۳۹۰×۸۴۴** موفق شد. خروجی تصویری فقط در `.data/ui-smoke` لوکال می‌ماند و به Git اضافه نمی‌شود.
- همین آزمون روی SQLite توسعهٔ یکبارمصرف و endpointهای محلی انجام شده؛ ارسال پیامک/پول واقعی، مرورگرهای iOS/Android واقعی، و کاربران/ترافیک production را شبیه‌سازی نمی‌کند.

اجرای محلی e2e نیازمند Chromium/Playwright و کتابخانه‌های runtime سازگار با سیستم‌عامل است. اطلاعات یک مدیر موقت را فقط در مسیر gitignored نگه دارید؛ تست هرگز به production وصل نشود:

```sh
mkdir -p .data
node -e "const fs=require('fs');if(!fs.existsSync('.data/ui-preview-auth.json'))fs.writeFileSync('.data/ui-preview-auth.json',JSON.stringify({username:'preview_admin',password:require('crypto').randomBytes(24).toString('base64url')}),{mode:0o600})"
# محیط dev/test یکبارمصرف SQLite را طبق docs/INSTALL.md بالا بیاورید؛ از بانک عملیاتی استفاده نکنید.
SMOKE_AUTH_FILE=.data/ui-preview-auth.json npm run test:browser --workspace apps/web
```
