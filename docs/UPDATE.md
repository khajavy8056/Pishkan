# به‌روزرسانی و بازگشت

## اصل حاکم

به‌روزرسانی هرگز نباید مشتری، پرونده، فاکتور، تراکنش، تنظیمات یا حساب مدیر را حذف کند.
پشکان با سه مکانیزم این را تضمین می‌کند:

1. **مهاجرت‌های نسخه‌بندی‌شده** (`apps/api/migrations/00N_*.sql`): فقط `CREATE TABLE IF NOT EXISTS`،
   `ALTER TABLE ... ADD COLUMN` و داده‌های اولیه. هیچ مهاجرتی `DROP` روی جدول داده ندارد.
   شماره مهاجرت‌های اجراشده در جدول `schema_migrations` نگه داشته می‌شود.
2. **انتشار نسخه‌ها در مسیرهای جدا** (`/opt/pishkan/releases/<timestamp>`) و فعال‌سازی با لینک نمادین اتمیک.
3. **بازگشت خودکار**: اگر سرویس جدید سالم بالا نیاید، نسخه قبلی فعال می‌شود.

## به‌روزرسانی استاندارد

```bash
sudo pishkan update            # خودش آخرین نسخهٔ شاخه را پیدا می‌کند
sudo pishkan update --dry-run  # فقط بگو چه چیزی عوض می‌شود
```

> برای تنظیم دامنه، زیردامنه و TLS، **[DEPLOY.md](DEPLOY.md)** را ببینید.
> برای قاعده‌های توسعه (expand/contract)، **[UPDATING-FOR-DEVELOPERS.md](UPDATING-FOR-DEVELOPERS.md)**.

مراحل داخلی:

1. پشتیبان‌گیری خودکار (پایگاه داده + مدارک) در `/var/backups/pishkan`.
2. `git clone --depth 1` از شاخه `main` در مسیر نسخه جدید.
3. `npm ci` و ساخت API و وب؛ در صورت خطای ساخت، نسخه فعلی دست‌نخورده می‌ماند.
4. اجرای مهاجرت‌ها؛ در صورت خطا، نسخه جدید رها و نسخه فعلی حفظ می‌شود.
5. تغییر لینک `current`، بازنویسی سرویس systemd و راه‌اندازی مجدد.
6. بررسی `/api/health` تا ۹۰ ثانیه؛ در صورت شکست، بازگشت خودکار به نسخه قبلی.

### گزینه‌ها

```bash
sudo pishkan update --ref <SHA-کامل-۴۰-رقمی>   # نصب یک commit مشخص
sudo pishkan update --no-backup                # فقط وقتی پشتیبان تازه دارید
```

## ارتقای ۱٫۳٫۰ → ۱٫۴٫۰

مهاجرت `019_staff_earnings_and_withdrawals.sql` فقط افزایشی است:

1. هفت ستون به `compensation_contracts` و هفت ستون به `compensation_entries` اضافه می‌شود؛
   چهار جدول تازه ساخته می‌شود (`staff_withdrawals`, `staff_withdrawal_events`,
   `staff_salary_payments`, `request_claim_attempts`) و سه ستون به `requests`.
2. هیچ ستون/ردیف/مبلغی حذف یا بازنویسی نمی‌شود. آزمون ارتقا روی دادهٔ نسخهٔ قبل نشان داد
   ستون‌های موجود شش جدول پس از مهاجرت **بایت‌به‌بایت** یکسان می‌مانند.
3. ردیف‌های درآمد قدیمی بدون `percent`/`basis_amount` باقی می‌مانند (`0`)؛ مبلغ اصلی آن‌ها
   دست‌نخورده است و فقط ستون‌های تازه مقدار پیش‌فرض می‌گیرند.
4. پس از ارتقا، پیش از استفاده از صف درخواست‌های آزاد:
   - در تنظیمات، `services.auto_assign_strategy` را روی `queue` بگذارید تا پرونده‌های تازه
     خودکار ارجاع نشوند و در صف پذیرش بمانند.
   - در بخش «درآمد و تسویه کارکنان» برای هر کارمند قرارداد (درصدی یا حقوق ثابت) بسازید؛
     کارمند بدون قرارداد نه سهم درصدی دارد و نه حقوق ماهانه.
   - در صورت نیاز، دورهٔ تسویه و حداقل برداشت را سراسری یا در قرارداد همان کارمند تنظیم کنید.
5. بازگشت به ۱٫۳٫۰ با `pishkan rollback` انجام می‌شود؛ ستون‌ها و جدول‌های تازه برای کد قدیمی
   بی‌ضررند و داده‌های قبلی دست‌نخورده‌اند.

## بازگشت به نسخه قبلی

```bash
sudo pishkan rollback                 # آخرین نسخه پیشین
sudo pishkan rollback --to 20260101120000
```

بازگشت، **کد** را برمی‌گرداند. اگر نسخه جدید مهاجرت داده انجام داده باشد:

- ستون‌های جدید باقی می‌مانند (بی‌ضرر برای کد قدیمی در بیشتر موارد).
- اگر مهاجرت رفتار داده را تغییر داده باشد، ممکن است بازیابی پایگاه داده لازم شود:
  ```bash
  sudo pishkan restore /var/backups/pishkan/pishkan-backup-<timestamp>.tar.gz
  ```
- همیشه پیش از بازگشت، پشتیبان فعلی را نگه دارید (`sudo pishkan backup`).

## یادداشت ارتقا از ۱٫۲٫۰ به ۱٫۳٫۰

- مهاجرت `018_wallet_gateway_monitoring.sql` به‌صورت افزایشی اجرا می‌شود: جداول جدید (`wallets`, `wallet_transactions`, `payment_callbacks`, `system_logs`, `metric_samples`, `alerts`) و ستون‌های تازهٔ `payments` (`purpose`, `wallet_id`, `provider_reference`) و ایندکس‌ها؛ **هیچ ستون یا ردیف مالی حذف نمی‌شود**.
- مجوزهای نقش‌های سیستمی یک بار با نشانگر `system.permissions_version = 2` همگام می‌شوند: فقط مجوزهای جدید (`wallet.*`, `monitoring.*`, `logs.*`, `alerts.*`) اضافه می‌شوند و مجوزهایی که مدیر قبلاً برداشته است برنمی‌گردند.
- پس از ارتقا: در «تنظیمات → حسابداری و پرداخت» درگاه را تنظیم کنید (شبیه‌ساز برای آزمون، زرین‌پال برای واقعی)، «کیف پول مشتریان» را بررسی کنید و در «زیرساخت → مرکز پایش» سلامت را ببینید.
- **پرداخت نقدی/دستی دیگر در دسترس نیست.** اگر کارکنان از روش نقدی استفاده می‌کردند، پیش از ارتقا رویه را به «شارژ کیف پول با دلیل + تسویه از کیف پول» تغییر دهید. فاکتورهای نقدی قبلی و سوابق دست‌نخورده و فقط خواندنی می‌مانند.
- پرداخت‌هایی که **در حین ارتقا** در درگاه باز بودند از مسیر قدیمی callback (`/api/accounting/gateway/zarinpal`) تسویه می‌شوند؛ پرداخت‌های جدید از `/api/payments/callback/:provider` استفاده می‌کنند.

## رویه توصیه‌شده برای به‌روزرسانی روی سرور عملیاتی

1. اطلاع‌رسانی به کاربران در ساعات کم‌ترافیک.
2. `sudo pishkan backup` (علاوه بر پشتیبان خودکار به‌روزرسانی).
3. انتقال نسخه پشتیبان به مقصد خارج از سرور (`docs/BACKUP-RESTORE.md`).
4. `sudo pishkan update`.
5. بررسی سریع: ورود مدیر، باز شدن کاتالوگ، ثبت یک درخواست آزمایشی، مشاهده داشبورد.
6. در صورت مشاهده مشکل: `sudo pishkan rollback`.

## چرخه عمر نسخه‌ها

- نسخه‌های فعال و قبلی در `/opt/pishkan/releases` می‌مانند.
- برای پاک کردن نسخه‌های قدیمی (فقط پس از چند روز پایداری):
  ```bash
  ls -1dt /opt/pishkan/releases/*/ | tail -n +4 | xargs -r sudo rm -rf
  ```
  حداقل دو نسخه آخر را نگاه دارید تا `rollback` ممکن بماند.

## به‌روزرسانی دستی (بدون CI/CD)

```bash
cd /opt/pishkan/current
sudo -u pishkan git pull        # فقط اگر این مسیر خودش مخزن گیت باشد
sudo -u pishkan npm ci
sudo -u pishkan npm run build
sudo pishkan migrate
sudo systemctl restart pishkan-api
sudo pishkan health
```

توصیه: به‌جای این روش از `pishkan update` استفاده کنید تا امکان بازگشت خودکار حفظ شود.
